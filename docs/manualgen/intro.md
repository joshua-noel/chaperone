# The `chap` manual

> **Generated. Do not edit this file.** `go run ./docs/manualgen` writes it from the `chap` binary's own help and from `api/manual.yaml`; the prose is in `docs/manualgen/intro.md`. `go test ./docs/manualgen` fails when this file is out of date. For what a given token may use right now, ask chapd: `chap manual`.

`chap` is the command-line client of `chapd`, Chaperone's daemon. An agent (or the orchestrator) calls `chap`; `chap` makes one or two HTTP calls to `chapd` and prints the answer. `chapd` decides: policy, approvals and the ledger live there, not in `chap`.

## Before you start

| | |
| --- | --- |
| **Credential** | `CHAP_RUN_TOKEN` if it is set (a run's token); otherwise the orchestrator token file: `CHAP_ORCHESTRATOR_TOKEN_FILE`, else `%LOCALAPPDATA%\Chaperone\orchestrator.token`. No flag takes a token. |
| **chapd address** | `CHAP_URL` (default `http://127.0.0.1:55398`). Only a loopback address is accepted. |
| **Project** | A run's project is in its token. The orchestrator names one with `--project` or `CHAP_PROJECT`. |
| **Output** | Plain lines, no colour. `--json` prints chapd's JSON reply and nothing else on stdout. |
| **Waiting** | `--wait <s>` holds the call up to 55 s for a final state. `chap op show <id> --wait 30` follows an op that is not finished. |

## Asking for something that needs a person

`--request --reason "<why>"` creates the approval card for the exact op and returns at once. The operator reads the card in the console and approves it with Windows Hello (or the phone). `chap` has no way to approve; `chap approve list` only shows your own requests. When the card is approved, repeat the same command with `--approval <a-id>`. The approval is bound to the exact request: a different head, recipient or parameter needs a new card.

## Reading a denial

```
DENIED pr.merge on acme/shop#214 (profile docs, run r-7f3a)
cause: OP_NOT_IN_TOKEN
why: pr.merge is not in this run's token
request: chap request scope --reason "<why the task needs pr.merge>"
```

`DENIED <op> on <target>` names what was refused and what it was aimed at. `cause` is the cause code (stable, safe to match on), `why` is chapd's reason. The last line says what to do: `request` is the exact command that asks for what was refused; `next` is a plain next step for a cause that asking cannot fix but you can act on (a stale branch: ask the orchestrator to update it; a red check: fix the code; a flood of waiting requests: wait for the operator; a malformed request: correct it; a run whose token has expired or whose token was revoked: stop). A `next` line does not offer a way round a control. When nothing you can do changes the answer the line is `request: not possible, policy does not allow asking` (for example an op that is not in your token). A refusal that happens after the op was allowed (`chap pr open` answers `refused`) carries the same denial, printed under the op's checks and shown again by `chap op show <id>`; the checks are those of the request and say nothing about the refusal. Repeating a refused ask is counted; past the policy's threshold the denial carries `note: repeated attempt ...` and is flagged as thrash.

## When chapd says a profile is not admitted

A run token from the runner names its profile by digest. `chapd` admits the token only when its profile folder (`-profiles-dir`) holds a file with that digest that still hashes to its name. `TOKEN_INVALID: profile digest sha256:... is not admitted` means it does not (an unknown digest, or a file that was edited); `no profile source is configured` means `chapd` was started without a profile folder. Neither is something the run can fix: tell the operator. The steps are in `docs/runbooks/runner-profiles.md`.

## Op classes

| Class | Meaning |
| --- | --- |
| routine | Allowed inside the token's scope and the policy. No approval. |
| gated | Allowed only when the op's own checks pass (for `pr.merge`: `verify` green on the exact head, the base current). Some checks can ask for an approval (a medium-risk PR). |
| high | Always needs one approval bound to the exact request. |
| critical | High, plus the CRITICAL label on the card and an alert on request, approval and execution. |

An op that policy has not enabled is refused with `OP_DISABLED`. Enabling one is a pull request that changes `internal/policy/data/baseline.yaml`.
