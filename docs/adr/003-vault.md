# ADR-003: Vault: where Chaperone keeps credentials, and how agents never see them

- **Status:** **Accepted** (operator sign-off). Amended 2026-10-24 for the separate agent account, one-device approval, the phone passkey, the orchestrator token and the critical class for secrets, and 2026-11-18 for key wrappers on macOS and Linux (amendment 6): see "Amendments" at the end.
- **Credentials in scope for Phase 1:** GitHub App private key; Google OAuth refresh token(s) (mail, Drive); the ntfy topic and any notifier token; Chaperone's own keys (interim run-token issuer key, ledger anchor signing key, execution-grant signing key). Later: Notion, Resend, deploy targets, model providers.
- **Incidents this answers:** 19 Oct (a secret key printed into an agent log); and today's reality that agents hold the operator's GitHub token.

## Context

- Before the runner exists, agents used to run as the operator on the server, and anything the operator account can read, an agent can read. **A later decision ends that before Phase 1 ships:** agents run under their own low-privilege Windows account (the "agent account"), the operator account (where the orchestrator, the lead agent also called "the orchestrator", runs) is a third principal, and `svc-chaperone` is the fourth. The vault still cannot live in the operator's DPAPI scope, Credential Manager, or any file the operator account can read, because the operator account also holds the orchestrator token (ADR-007) and any malware running as the operator account is outside the agents' sandbox. Until the accounts are created, the old shared-account situation holds and is a recorded accepted risk (RT-06, RT-07).
- DPAPI (`CryptProtectData`): typically only a user with matching logon credentials can decrypt, and only on the same computer. With the flag `CRYPTPROTECT_LOCAL_MACHINE` **any user on the machine can decrypt**, so that flag is forbidden here. An application-specific `pOptionalEntropy` blob can be supplied. (<https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata>)
- Credential Manager credentials: `CredentialBlobSize` cannot exceed `CRED_MAX_CREDENTIAL_BLOB_SIZE` (5*512 = 2560 bytes) (<https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentiala>). Credentials belong to the logon user, so the same-user problem applies.
- age is a file format with "multiple pluggable recipients"; a file header carries one or more recipient stanzas and a MAC (<https://age-encryption.org/v1>). The Go implementation is `filippo.io/age` v1.3.2 (<https://pkg.go.dev/filippo.io/age>).
- `x/sys/windows` exposes `CryptProtectData` and `CryptUnprotectData`, so DPAPI needs no cgo (<https://pkg.go.dev/golang.org/x/sys/windows>).
- WSL distros belong to the Windows user that registered them `[INFERENCE: standard WSL behaviour, not yet checked on the server]`, so a dedicated service account **cannot** run `wsl -d <pilot distro>`. This shapes the deploy adapter (ADR-004's `chap-host`) but not the vault.

## Decision

**Envelope vault: one age file per secret, with the age identity wrapped by DPAPI under a dedicated service account, plus an offline recovery recipient.**

```
D:\Chaperone\data\vault\<secret_id>.age      one file per secret; ciphertext only
D:\Chaperone\data\vault\index (SQLite)       id, kind, project, owner, fingerprint, created, rotated, last_used
<svc-chaperone profile>\...\vault-identity.dpapi      age X25519 identity, wrapped with CryptProtectData (user scope, own entropy)
offline (operator's safe, never on the server)         recovery age identity (printed / USB)
```

1. **Service account.** `svc-chaperone`, a local standard user (not admin), "Log on as a service" only, no interactive logon, no remote access. `chapd` runs as this account. Its DPAPI master key lives in its own profile, which the operator account (and so any agent) cannot read without an elevated token. Folder ACLs: `D:\Chaperone\data\` full control for `svc-chaperone` and SYSTEM; no access for the operator account, except the read-only ledger export folder (ADR-006). Creating the account and ACLs is a **human-gated, elevated** step; agents never run it.
2. **Encryption.** Every secret is encrypted to two age recipients: the **service recipient** (public half of the identity above) and the **recovery recipient** (public half only is on the server). Losing the server profile, or DPAPI breaking after an account reset, is recoverable by the offline identity; the ciphertext files are safe to include in the existing backup set.
3. **`KeyWrapper` interface.** DPAPI is one implementation (`dpapi-user`). The interface exists so Stage B can swap in a TPM-sealed key, `systemd-creds`, or a cloud KMS without touching the vault format. Phase 1 ships only `dpapi-user`.
4. **Use, never read.** The only internal API is `vault.Use(ctx, id, func(secret []byte) error)`. The secret exists in memory only inside the closure, which belongs to an adapter (GitHub, Google, ntfy, grant signer). **No HTTP route, CLI command or ledger field returns a secret value.** `secrets.*` ops expose metadata only (id, kind, fingerprint, age, last used). Fingerprint = `HMAC-SHA256(vault_fp_key, secret)` truncated, so an agent or log cannot confirm a guessed value.
5. **Import and rotation** go through the console, as a `secrets.write` op: class **critical**, approved with **one device**: Windows Hello on the server or the phone passkey with number matching (ADR-004). The page posts the value straight to `chapd`; the value is never logged, never put in a URL, and the page sets `Cache-Control: no-store`. The GitHub App `.pem` is imported once and the downloaded file is deleted by the operator.
6. **Redaction at every boundary.** One `redact` package, used by the HTTP response writer, the ledger append, the log handler and the CLI's output: (a) exact-match registry of every secret fingerprint's current value in memory; (b) pattern rules for `ghs_`/`ghp_`/`github_pat_` (note the `ghs_` token is now ~520 characters and base64url JWT-shaped; do not use the old 40-character regex; see ADR-002), Anthropic and Google key prefixes, PEM blocks (`-----BEGIN`). A hit replaces the value and raises `REDACTION_BLOCKED` (a denial cause code in the spec) with a ledger event.
7. **Memory and dumps.** Zero secret buffers when the closure returns (best effort in Go). Do **not** depend on Go 1.26's experimental `runtime/secret` (<https://go.dev/doc/go1.26>); revisit when it leaves experiment. Turn off crash dumps for `chapd.exe` `[INFERENCE: via Windows Error Reporting LocalDumps registry settings; how is not yet checked]`.
8. **Canary secrets.** The test suite stores a canary value in the vault, runs every op, and asserts the canary string and its base64/hex forms appear **nowhere**: not in responses, ledger rows, JSONL exports, logs, `chap` output, panic traces, or the SQLite file. This is the regression test for the 19 Oct incident.

## What this does and does not defend (honest limits)

| Attacker | Result |
| --- | --- |
| Agent as the agent account, normal (non-elevated) token | Cannot read `svc-chaperone`'s profile DPAPI master key, the identity file, the vault folder, `chapd`'s memory, or the operator's profile (where the orchestrator token file lives). Can still call `chapd`'s API with its run token, which is the point. |
| Anything running as the operator account | Cannot read the vault or `state.db` either (the ACLs above exclude the operator account), but can read the orchestrator token file (ADR-007) and ask `chapd` for whatever that token's scope allows. High-impact asks still need an approval. |
| Agent that obtains an **elevated** token | Can read everything. Mitigation is UAC prompts on the secure desktop (`[INFERENCE: UAC is at its default on the server; not checked]`), and the house rule that agents run no elevated command. |
| Someone with the disk image, offline | Needs the `svc-chaperone` profile's master key (derived from that account's password); BitLocker on `D:` and `C:` is recommended `[INFERENCE: BitLocker status unknown]`. |
| Malware running **as `svc-chaperone`** (i.e. a bug in `chapd`) | Full access. Mitigation is the small dependency allowlist (ADR-001) and no code loading. |
| Loss of the server profile or reset of `svc-chaperone` | Recover with the offline identity; re-wrap with a new DPAPI identity. See the [vault recovery runbook](../runbooks/vault-recovery.md). |

## Alternatives

| Option | For | Against | Verdict |
| --- | --- | --- | --- |
| **age files + DPAPI-wrapped identity + offline recovery recipient** | Standard, reviewed format; multi-recipient gives recovery; Windows-bound part is one small interface; secrets are plain files so backup and restore are trivial; no extra service. | Two layers to explain; DPAPI binds to one account and machine; needs the service account. | **Chosen** |
| DPAPI only (one `CryptProtectData` blob per secret) | Simplest. | No recovery path; format is Windows-only and undocumented to other tools; Stage B would re-key everything. | Rejected |
| Windows Credential Manager | Built in. | 2,560-byte limit per credential (a 2048-bit RSA PEM is near it; a larger key or a JSON token set will not fit); same-user scope; no recovery; harder to back up. | Rejected |
| Embedded KMS / secrets server (OpenBao / Vault transit, cloud KMS) | Audit, leases, rotation, transit without exposing keys. | A second service with unseal or cloud-KMS dependence (auto-unseal needs a root of trust we do not yet have on one server); ~10 secrets do not justify it; not evaluated in depth `[INFERENCE]`. | Revisit at Stage B or with more than one approver |
| TPM-sealed key (CNG Platform Crypto Provider) | Non-exportable key; strongest at rest. | Harder from Go under a service account; hardware-bound with no recovery by itself; I could not fetch Microsoft's current provider doc (404), so the details are unverified. | Planned as a second `KeyWrapper` |

## Verify

- Vault: round-trip test; wrong-account decrypt fails (Windows CI job); recovery-identity decrypt works; fingerprint never reveals value; `Use` closure leaves no copy in returned errors.
- The canary-secret test above, and a test that the `chap` process can never print a secret even if `chapd` is told to (the API has no such route).

## Amendments (2026-10-24, first build)

**Amendment 1. Account split.** The human step that creates accounts now creates two accounts, `svc-chaperone` and the agent account, and a reviewed script launches the factory's agents under the second one. Every "agent as the operator account" statement above is superseded by the row for the agent account. The operator account remains excluded from the vault folder and `state.db`.

**Amendment 2. `secrets.*` is critical.** `secrets.write` (import, rotate) and any later `secrets.*` op are class critical: never auto-allowed, always an approval card bound to the exact op hash, logged loudly (an alert on every approval and every use). `secrets.*` ops still expose metadata only; no op returns a value.

**Amendment 3. One device.** Approving a `secrets.*` op does not need two devices. The compensating controls are the ones already here: the card is rendered by the server and its hash is in the challenge, the console binds `Host` and `Origin`, and nothing a request can carry is a secret value.

**Amendment 4. Accepted residual risk: split or re-encoded secrets (RT-25).** The redactor (section 6) masks a registered secret's raw bytes and the forms the registry derives from it (standard, raw, URL-safe and raw-URL base64, lower- and upper-case hex, the JSON-escaped text, and a CRLF/LF swap), plus the pattern rules. It does **not** find a secret that was cut into pieces (`ghp_abc` + `def...` sent as two params, or one character per line), or that was transformed by anything else (rot13, reversed, gzip then base64, URL-encoding with percent escapes, a character per request, a cipher the sender holds the key to). Matching those needs the secret to be re-derived by the same transform, and no filter can list every transform. We accept this because an agent that can send those pieces already holds the secret; the redactor exists to stop `chapd` and `chap` from **echoing or storing** a secret, which is what the 19 Oct incident was, and it blocks that. What bounds the damage: the agent account cannot read the vault, `state.db` or the key files (the table above); every high-impact op is approved on a card that shows the exact params (ADR-004); the ledger redacts every event as it is written; and the canary suite fails the build if any registered form shows up. Revisit with entropy or length-based detection when a real case shows the need; it will add false positives to ordinary params.

**Amendment 5. The Linear intake: a second service credential in the vault.** `chapd` holds two more vault secrets, `linear-client-id` and `linear-client-secret` (kind `linear-oauth-client`; a vault id takes no dot), the client of a Linear OAuth app with client credentials enabled. They are read through `Vault.Use` only, to ask Linear's token endpoint (`grant_type=client_credentials`, HTTP Basic, scope `read,write`) for a bearer token. The token is held the way ADR-002 holds GitHub tokens (never written anywhere) and capped in time: it lives in `chapd`'s memory only, for at most one hour although Linear issues it for 30 days, is replaced after a 401, is registered with the redaction registry while held, and is never in a log line, a ledger event or an op result (`internal/connectors/linear/token.go`; tests: `TestTokenIsNeverKeptLongerThanTheCap`, `TestACallRefetchesTheTokenAfter401`, `TestTheTokenIsRegisteredForRedaction`, and the ledger scan in `cmd/chapd` `TestIntakeAllowedOpsAreLedgered`). Four ops use it (`intake.list`, `intake.comment`, `intake.move`, `intake.states`), all class routine, orchestrator token only, and off in the baseline until a policy PR turns them on.
- **Why `write`.** Linear has no scope that moves an issue to a state and does nothing else (`comments:create` and `issues:create` do not cover a state change), so the app holds `write`, which reaches the whole workspace. The guard is Chaperone's policy, not the app: the project file's `linear:` block names **one team key, one label and the state names `intake.move` may set** (`internal/policy/linear.go`); `chapd` sends **five fixed GraphQL documents** and the caller supplies no query, no team, no label and no state id; a write is allowed only on an item of that team that carries the label **at the moment of the write** (read in `Check`, and again in `Execute` with the token that writes); the Engineering team is refused by key and by name; and the mutations carry only the fields they need (a comment: id, issue, body; a move: the state id), so no label, title, description, assignee, archive or delete change can be sent. The operator's amendment is enforced as written: **the `claude` label is never removed.** A team restriction on the app is used as well when the plan offers it (runbook step 1); the policy does not depend on it.
- **The residual window.** Linear has no conditional update, so the label can change in the milliseconds between the second read and Linear's answer. A write in that window lands on an item that has just lost the label. Accepted: the writes are a comment and a state move on the operator's own board, both reversible by a person.
- **Reads.** `intake.list` returns the open items with state, title, description, comments (at most 8), links and update time, from a cache that a poller refreshes every 15 minutes (`-linear-poll-interval`; `intake.list refresh` reads at once, at most every 30 s per board). Board text is untrusted data: it is cleaned, capped, flagged `untrusted_text`, and an item whose text looks like a secret is withheld. The cache is memory only.
- **Rate limits.** The policy pack's `rate_per_minute` per caller and op, a budget of 300 Linear calls in any 60 minutes in `chapd`, and a stop on Linear's own signals (429, `RATELIMITED`, 20 or fewer requests remaining) until the time Linear names.
- **Writes are sent once.** A definite refusal by Linear is `failed`; an answer that does not show whether Linear acted leaves the op `unconfirmed` and names the comment id (derived from the execution id) so the comment can be looked up.
- **A fix found on the way.** The redaction registry now also masks the **trimmed** form of a value that was saved with trailing white space (a console paste or an editor adds a newline; the connector uses the trimmed value, so only the trimmed form shows up in a comment or a log). Before this, such a secret passed the redactor when it appeared without its newline (`internal/redact/registry.go`, `TestExactValueSavedWithTrailingWhitespaceIsMaskedWithoutIt`). Amendment 4's list of derived forms gains this one.
- **Not decided here.** Whether the orchestrator's pickup comment must be a fixed template (it is free text up to 4 000 bytes today); a webhook instead of polling (needs a public HTTPS endpoint, ADR-004 rejects one for phase 1).

**Amendment 6. The vault off Windows: three more key wrappers (v1).** The vault could not hold a secret on macOS or Linux, because the only `KeyWrapper` was Windows DPAPI. The interface, the age file format and the rule that the index records the wrapper's name are unchanged. Three wrappers are added. All three are pure Go: no cgo, no new module.

| Name (stored in the index) | System | Default there | Where the key lives | Needs |
| --- | --- | --- | --- | --- |
| `dpapi-user` | Windows | yes | DPAPI, current-user scope (unchanged) | nothing |
| `keychain-macos` | macOS | yes | the user's login keychain | `/usr/bin/security`, an unlocked keychain |
| `secret-service` | Linux | yes | a Secret Service keyring (GNOME Keyring, KWallet) | `secret-tool`, a session bus, an unlocked keyring |
| `age-passphrase` | any | no | nowhere: derived from a passphrase | a person or a pipe to give the passphrase |

- **Choosing.** `chapd vault ...`, `chapd connect google ...` and `chapd run` take `-vault-wrapper NAME`. Without it the default for the system is used. For another system (FreeBSD, for example) there is no default and the command says so. `-vault-passphrase-fd N` goes with `age-passphrase` only.
- **No fall back.** If the default cannot work (no `secret-tool`, no `security`), the command stops with a message that names the cause and the `age-passphrase` option. It never tries another wrapper, and `chapd` never writes a key to a file of its own: the key files hold a reference (keychain wrappers) or an age blob (passphrase). Where the key is then kept is the keychain's business, with the limits in the table below. The wrapper's name is stored in the index at `init`; a vault opened with another name fails with `created with key wrapper "X", opened with "Y"`.
- **Moving a vault to another wrapper** is `chapd vault recover -vault-wrapper NEW` with the offline recovery identity. It re-keys every secret under the new wrapper and records the new name. Nothing else changes a vault's wrapper.
- **Key file names.** The files stay `vault-identity.dpapi` and `vault-fpkey.dpapi` on every system, so existing vaults and backups need no rename. The suffix is history, not a statement about the wrapper.

*Evaluation of the ways to reach a keychain without C code.*

| Way | Verdict |
| --- | --- |
| macOS `security add-generic-password -w VALUE` | **Rejected.** The value is in the argument list, which any process of the same user can read with `ps`. The tool's own manual calls `-p` and `-w VALUE` insecure. |
| macOS `security add-generic-password -w` (no value) | **Rejected.** It asks through `getpass()` (checked in Apple's `keychain_add.c`), which reads the terminal. A program has no terminal to give it, and whether it falls back to standard input is not something to depend on. |
| macOS `security -i`, commands on standard input; read back with `security find-generic-password -w` | **Used.** In `-i` mode the tool reads each command from standard input (4096 bytes a line; quotes, white space and backslashes are the only syntax), so the value is never an argument. `find-generic-password -w` prints only the value on standard output. Checked against Apple's published source of the tool (`SecurityTool/macOS/security.c`). **Not run on a Mac yet.** |
| Linux `secret-tool store` (secret on standard input), `secret-tool lookup` (secret on standard output) | **Used.** `store` reads the secret from standard input up to 8192 bytes; only the attribute names and a random id are arguments. Checked against libsecret's `secret-tool.c`. **Not run on a Linux desktop yet.** |
| A pure-Go D-Bus client talking to the Secret Service | **Not used.** It needs a new module on the allow-list (ADR-001) and more code to review than a call to a tool that every Secret Service install ships. Revisit if `secret-tool` proves a poor fit. |
| age scrypt passphrase | **Used** for machines with neither. `filippo.io/age` and `golang.org/x/crypto/scrypt` are already vendored. |

*How the keychain wrappers hold a key.*

- **The blob holds no key.** `Wrap` makes a random 128-bit id, stores the key in the keychain under that id (lower-case hex, so no store has to cope with binary data or quoting), reads it back, compares, and returns a three-line reference (`chaperone-key-reference v1`, the wrapper's name, the id). There is no encryption layer of our own; the protection is the keychain's. If the read back fails, the item is deleted and `Wrap` returns an error.
- **`Unwrap` accepts one shape only:** that magic line, this wrapper's own name, and exactly 32 lower-case hex digits. The id reaches a command line, so nothing else is passed on.
- **The program is a fixed absolute path** (`/usr/bin/security`; `secret-tool` in `/usr/bin`, `/bin`, `/usr/local/bin` or `/run/current-system/sw/bin`), never a PATH lookup, so a program another process put on PATH cannot receive a key. On Unix the file and the folder it is in must also be owned by root and writable by nobody else (not the group, not others); a tool that fails this is reported as "not trusted" and not run. This keeps `/usr/local/bin` in the list, because on a normal Linux it is root-owned and passes; a user-owned folder (a Homebrew prefix) or an admin-group-writable one does not. The check reads the owner and mode of the file after symlinks are followed, and of the folder named in the search list as it is named there. It does not look at the folder that holds a symlink's target (on NixOS, the store folder behind the link), nor at any folder above the search-list folder. It is a check of the state at that moment, not a lock.
- **Output buffers have a fixed size** (16 KiB), so a growing buffer leaves no stale copy of a key. They are zeroed after use. A tool that writes more is an error.
- **Errors never hold a key.** A tool's standard error is shown, cut to 200 printable characters, unless it contains the key (some tools echo their input), in which case it is withheld.
- **Both tools are given 2 minutes**, because the keychain may be asking the user to unlock it.

*How the passphrase wrapper works.*

- The blob is an ordinary age file with one scrypt recipient (work factor 2^18, about one second, 256 MiB). `age -d` with the same passphrase opens it. On unwrap a blob that asks for more than 2^20 (1 GiB) is refused before any work is done, so a planted file cannot make `chapd` allocate gigabytes or spend minutes in scrypt. `chapd` itself only writes 2^18; age's own default cap of 2^22 would allow 4 GiB.
- **The passphrase is never a flag or an environment variable.** It comes from the terminal (`/dev/tty`, or the console on Windows), read with echo off, with a prompt for the new passphrase and a second prompt to repeat it; or from the first line of a file descriptor (`-vault-passphrase-fd N`), for a service: `systemd-creds decrypt secret.cred - | chapd run -vault-wrapper age-passphrase -vault-passphrase-fd 0 ...`. If echo cannot be turned off, nothing is asked. A signal (interrupt, terminate, hang-up, quit) ends the prompt and restores the terminal, and the command stops with the error "interrupted" (`chapd vault recover` too: it does not go on to ask for a new passphrase). The signal is not raised again, so the exit status is 1, not the signal's: killing the process from inside a library would skip the deferred clean-up of its caller. A kill that cannot be caught (SIGKILL) cannot restore the terminal.
- **Which descriptors are accepted.** The descriptor is opened and checked while the command line is parsed, before `chapd` opens a log file, the database or anything else that could be given that number. A **pipe or FIFO** is accepted on any descriptor. A **regular file** is accepted on descriptor 0 only (`< file`, or `StandardInput=file:...` in a service unit): on any other number a regular file is almost certainly one `chapd` opened itself. A **terminal is refused** (the passphrase would be shown and not asked twice; leave the flag out to be asked there). On Windows a terminal is a console, or the named pipe that mintty, MSYS2 and Cygwin use when the pseudo-console is off (a pipe called `\msys-...-pty...` or `\cygwin-...-pty...`, found with `GetFileInformationByHandleEx`, as go-isatty does). Also refused are sockets, devices, descriptors 1 and 2, and a descriptor that is not open. A descriptor above 0 is duplicated and the duplicate is read and closed. The original is **left open on purpose**: only its number is known, and closing a descriptor this code did not open could close something else. After it passes the checks the original is marked close-on-exec, so a child process that `chapd` starts does not inherit the read end of the passphrase pipe; a refused descriptor is not touched. On Windows only descriptor 0 exists. `chapd vault recover` refuses `-vault-passphrase-fd 0` (exit 2), because it reads the recovery identity from standard input.
- A new passphrase must have at least 16 characters, **for now**: the owner has not yet confirmed the number. This is a floor, not a strength test.
- The wrapper keeps the passphrase in memory only while one operation (`init`, `open`, `recover`) runs, so `init` asks once, not once per key. The vault makes the wrapper forget it when the operation ends, and a failed passphrase is never kept. `chapd run` therefore zeroes its own copies of the passphrase once it has opened the vault; copies inside age (it makes its own from a string) may remain until that memory is reused.
- **Recovery after a forgotten passphrase:** `chapd vault recover` first tries to open the vault, so it asks for the old passphrase once. Press Enter, or type anything: the open fails and recovery goes on, asks for a new passphrase twice, and needs the offline recovery identity.

*What each wrapper protects against, and what it does not.*

| Attacker | `dpapi-user` (as before) | `keychain-macos` | `secret-service` | `age-passphrase` |
| --- | --- | --- | --- | --- |
| Someone who copies the vault folders (a backup, a stolen disk) but not the user's keychain or passphrase | Protected | Protected only as far as the login password resists guessing, if the keychain file is on the same disk (a stolen disk or full backup holds both); not protected if the keychain has an empty password. The key files alone are only references | Protected only as far as the keyring password resists guessing, if the keyring file is on the same disk; not protected with an empty keyring password (some desktops auto-unlock it, which is the same thing). The key files alone are only references | Protected as far as the passphrase resists scrypt guessing |
| Another user account on the same computer | Protected | Protected: the login keychain is per user | Protected: the keyring is per user | Protected as far as the passphrase resists guessing |
| **Any program running as the same user, including every agent that runs as that user** | Protected only if `chapd` runs as its own account (amendment 1) | **Not protected.** Any such program can run `security find-generic-password` while the keychain is unlocked. The item's access list cannot tell `chapd` from another program that calls the same tool `[INFERENCE: not checked on a Mac]`. | **Not protected.** Any such program on the session bus can ask the Secret Service for the item while the keyring is unlocked. | Protected while `chapd` is not running: the key is not in memory or on disk. **Not protected** while it runs: a program of the same user may be able to read `chapd`'s memory, depending on the system's rules for debugging other processes `[INFERENCE: not tested on either system]`. |
| Someone who has the user's login password or an unlocked session | Not protected | Not protected (the keychain unlocks with the login password) | Not protected, the same | Not protected only if they also lack the passphrase |
| Malware that logs keystrokes or reads the terminal | Not protected | Not protected | Not protected | Not protected: it sees the passphrase |
| Someone with the disk image and the user's login password, offline | Needs the account's master key | Needs the login password | Needs the login password | Needs the passphrase |
| A weak login or keyring password (the keychain files, copied with the disk, are attacked offline) | Not applicable | **Not protected.** The keychain wrapper is only as strong as the login password. | **Not protected.** The wrapper is only as strong as the keyring password, and none at all if it is empty. | **Not protected** if the passphrase is weak. Scrypt makes each guess cost about a second of one core, not impossible. |

- **So on macOS and Linux the separation of ADR-003's amendment 1 does not exist by itself.** The key is as safe as the user account. The agent account (a separate low-privilege user for the agents) is what keeps the agents away from the vault, as on Windows. Run `chapd` under an account the agents cannot use, and the keychain wrappers are then the right size. If agents and `chapd` share one user, `age-passphrase` with a descriptor fed at start-up is the stronger choice, and while `chapd` is stopped no key exists anywhere on the disk.
- **Memory.** Plaintext key buffers that this code owns are zeroed after use. Two things are not zeroed and cannot be with the current libraries: the passphrase as a Go string inside age (`age.NewScryptRecipient` takes a string and keeps its own copy), and the key text inside age's stream buffers. Go's experimental `runtime/secret` is still not relied on (item 7).
- **Left behind on purpose.** An item that a failed `init` leaves in the keychain stays there, unreferenced, and a `recover` leaves the old items, referenced only by the retired key files in `retired-<time>/`: the `KeyWrapper` interface has no delete. They hold old keys of vaults that were replaced. Delete them in Keychain Access (service `chaperone-vault`) or with `secret-tool clear service chaperone-vault id <id>`.
- **Not done here.** A TPM or Secure Enclave key; a pure-Go Secret Service client; `chap doctor` checks for the new wrappers.

*Checks that need a real machine.* The wrappers are tested here with fake tools and a fake terminal, and the Linux code was also run on Linux under WSL. These are not run yet:

- macOS: the sequence of `security -i`, `find-generic-password -w` and `delete-generic-password` on a real login keychain; the behaviour when the keychain is locked or the prompt is declined; the passphrase prompt on a real terminal (`VAULT_TEST_REAL_TTY`, see `internal/vault/passphrase_test.go`).
- Linux with a desktop: `secret-tool store` reading standard input, `lookup` returning no trailing newline, the unlock prompt, a headless session (expected: a clear error), and the real-terminal passphrase test (already run once under `script` in WSL).

**Amendment 7. The generic issue ops on Linear (5 Nov 2026).** Beside the four `intake.*` ops (amendment 5), `chapd` serves six generic ops on the same Linear credential: `issue.get`, `issue.list`, `issue.comment`, `issue.label`, `issue.move` and `issue.link` (declared in `internal/connectors/linear/linearspec`; code `internal/connectors/linear/issue.go`, `issue_queries.go`). They are for the orchestrator token: a custom key can never hold an `issue.*` op (`internal/ops/keyceiling.go`, ADR-008). The vault, the token and the 300-calls-an-hour budget are unchanged; the Linear app's scope stays `read,write` (no new scope: the label and link mutations are issue updates). Seven more fixed documents join the five of amendment 5 (`IssueGet`, `IssueList`, `IssueGuard`, `IssueLabelLookup`, `IssueAddLabel`, `IssueRemoveLabel`, `IssueLink`); a caller's values still reach Linear only as variables.

- **Policy.** The project file's `linear:` block gains an optional `issues:` block: `team`, `label` (the provenance label), `states`, `labels` (what `issue.label` may add or remove), `link_hosts`, `max_mentions` (default 0) and `comment` (default false). Without the block every `issue.*` request for Linear is refused. Like all project data it enables nothing; the five new names are `enabled: false` in the baseline. `issue.comment` is one name for two connectors (the GitHub op of ADR-002 amendment 11 and this one), so its baseline entry is on for GitHub: the Linear adapter's refusal of a project with no `issues:` block, and of a comment unless the block says `comment: true`, is what keeps it off for Linear. The two connectors share one rate budget, because the budget is per op name (6 a minute, 20 an hour per caller): a Linear comment counts against the error watcher's GitHub comments. It was not split, because a second name would be a second operation to declare, pin and document; the shared budget is the smaller risk. The `issues:` host list may not name `linear.app` or a subdomain (a link to Linear could point at a board item), and a comment or link that names an issue or a team page of the intake team is refused. `internal/ops.ByTarget` picks the adapter by `target.adapter`.
- **The operator board is out of reach (`intake_label_excluded`, found by the security review).** An issue in the intake team (`linear.team`) or carrying the intake label (`linear.label`, compared without regard to case) is never read, listed, commented on, labelled, moved or linked by an issue op, and a request that names the intake team or label as its target, filter or label to set is refused. The check is code, runs in `Check` and again in `Execute` (so a label or a team move between the two stops the write), and fails closed: an issue with more labels than one page shows is refused because it cannot be shown free of the intake label. The loader turns off the Linear issue operations of a project whose `issues:` block names the intake team or label (or has any other mistake): the block is dropped, the intake block and every other op of the project keep working, chapd logs a warning at start, and each refusal names the project, the file and the field (the same narrowing as a bad `pr.tiers` glob). No field of the block lifts the check (a test builds a block that bypasses the loader and still reaches no item). `intake.*` stay orchestrator-only (STANDARD 3.8 rule 11). **The text an agent writes is checked on a best-effort basis.** A comment body, a link URL and a link title are refused if they point at the intake board: they are read after HTML entities and percent-escapes are decoded until stable, HTML comments and tags (the text is checked with its tags in as well as without them, because an autolink or an anchor is shaped like a tag) and the markdown characters `\`, `*`, `_`, `` ` `` and `~` are removed and every dash is made a hyphen, and any text that then holds `linear.app` or an identifier of the intake team (`SHOP-12`) is refused. Text with an invisible or default-ignorable character (`untrusted.Hidden`), a full-width letter or digit, or a word shaped like an identifier (letters and digits, a hyphen, a digit) that mixes the Latin alphabet with Cyrillic, Greek, Armenian, Cherokee or Coptic letters is refused too; the variation selector of an emoji or a keycap passes, ordinary text in another language passes, a Greek letter in `120μs` or `Δt` passes, and a word written wholly in look-alike letters passes (it cannot become a backlink: Linear reads the ASCII identifier). This is a guard against accidental and simple references, not a barrier, and it was not tried against real Linear. An agent can always describe an item in words. The real protection is that the operations cannot act on the board: every read and every write of an issue is refused for an intake item, whatever a comment says. The policy knows the intake team's key and label only, not its name or id, so those are not matched.
- **Writes.** Only an issue that carries `issues.label` now, in `issues.team`. `issue.label` adds or removes one label at a time with Linear's own add and remove mutations, so a label a person set in between is never overwritten; the provenance label itself is never added or removed. `issue.move` sets a state from `issues.states`. `issue.link` takes an https URL whose host is in `issues.link_hosts` (exact match, no port, no user name). `issue.comment` refuses mentions beyond `max_mentions` and any secret-shaped text. No op creates, edits, assigns, archives or deletes an issue: `issue.open` and `issue.update` are not built, they wait for the operator's yes.
- **Reads.** `issue.get` and `issue.list` return Linear's text as `untrusted_text`, capped and withheld when it looks like a secret, like `intake.list`. A list is one page of at most 25 with an opaque cursor.
- **Declared with the connector kit.** The facts of the five new operations (name, class, parameters and their bounds, rate) are declared once in `linearspec`, pinned in `internal/connectors/pintable`, and the catalog entries and params schemas are generated from them. `issue.comment` is declared by both connectors; the catalog entry is the GitHub one, and `linearspec.IssueComment` is kept equal to it by a test. `issue.label` and `issue.comment` keep hand-written `chap` commands. All ten Linear operations pass the conformance suite with no known gap. See `docs/connectors.md`.
- **Residual windows.** As in amendment 5, Linear has no conditional update: the milliseconds between `Execute`'s second read and Linear's answer remain. `issue.link`'s idempotence rests on Linear keeping one attachment per issue and URL (the connector standard's research profile says so; not confirmed here).
- **Not verified against Linear itself.** Nothing here ran against Linear. The research profile proposes `issueUpdate` with a computed `labelIds` list for labels; this connector uses `issueAddLabel` and `issueRemoveLabel` instead because they cannot overwrite a concurrent edit. Those two mutations, `attachmentCreate` and the `issueLabels` name filter are written from the author's knowledge of Linear's GraphQL schema, not read from it today, and are exercised only against the fake. If Linear's schema differs, the op fails with Linear's own GraphQL error and nothing is written. The first real run belongs to the live test on a scratch workspace before the policy PR that turns the ops on.

**Amendment 8. The Sentry connector: a third service credential in the vault (21 Nov 2026).** `chapd` holds one more vault secret, `sentry-auth-token` (kind `sentry-auth-token`; a vault id takes no dot): the auth token of a Sentry internal integration with the scopes `event:read` and `event:write`, or `event:read` alone for the two reads. It is read through `Vault.Use` for every call and never kept: the client holds no copy and only a registration with the redaction check, which masks it in a log, a result and the ledger. It is sent in the `Authorization` header and nowhere else, to the one server the project's policy names. Six ops use it (`errors.list`, `errors.get`, `errors.resolve`, `errors.unresolve`, `errors.assign`, `errors.comment`, declared in `internal/connectors/sentry/sentryspec`). They are for the orchestrator token: a custom key can never hold an `errors.*` op (`internal/ops/keyceiling.go`, ADR-008). All six are off in the baseline.

- **A Sentry token reaches the whole organisation, so the policy is the guard.** The project file's `sentry:` block names `base_url`, `organization`, `projects` (the Sentry project slugs the ops may touch) and `assignees` (who `errors.assign` may use; empty means it refuses everyone). Like all project data it enables nothing. Without the block, or with a block that cannot be used, every `errors.*` request refuses, and the reason names the project, the file and the field. A mistake in the block turns off the Sentry ops only: the project's other ops and blocks keep working, and `chapd` logs one `Warn` at start (the same narrowing as a bad `pr.tiers` glob). A key the file format does not know still refuses the whole file.
- **The token goes to one exact host.** `base_url` comes from the policy, so the policy decides where the token is sent. The rule is a narrow allow rule and not a list of bad hosts: an https origin, a lower-case DNS name with at least one dot that is not an IP address, an optional port, and nothing after it (no user name, no path, no trailing slash). `policy.CheckSentryBaseURL` is the rule; the policy loader applies it, and the client applies it again before every request, so the rule does not rest on the file alone. No redirect is followed, whatever HTTP client is given, so a redirect cannot carry the token to another host. There is no relaxed mode for tests: the fake is an https server on the loopback and the test HTTP client sends every request to it.
- **The issue is read again before every write, and its project must be listed.** A write is refused for an issue whose project is not in `sentry.projects`, in `Check` and again in `Execute` (a project that changed between the two stops the write). The match is exact and made on Sentry's value as it is; Sentry's text goes into a message only after it is cleaned. Sentry has no conditional update, so the milliseconds between that read and Sentry's answer remain.
- **What comes back is an allow-list.** The client decodes the fields it lists and no others, so request bodies, cookies, headers, user data, local variables, tags, breadcrumbs and the exception's message of an event are never held. `errors.get` returns the title, culprit, level, status, count, first and last seen, and from the latest event the id, the time, the exception type and at most 10 frames (file, line, function, in-app). The text is Sentry's, so it is cleaned, capped, marked `untrusted_text`, and withheld when it looks like a secret. A title often holds the exception's message and so can hold personal data that the connector cannot recognise: the runbook says so.
- **Writes.** `errors.resolve` and `errors.unresolve` change only an issue that has the other status; an issue that already has it is left alone and nothing is sent, and an ignored (archived) issue is refused. `errors.assign` takes a member from `sentry.assignees`. `errors.comment` takes plain text of up to 2000 bytes: a narrow allow rule of letters, digits, spaces, line breaks and a few marks, so a note cannot hold an at sign or a number sign (a mention of a person or a team), markup, a link bracket or an invisible character, and any secret-shaped text is refused. No op deletes, merges, ignores or creates an issue, unassigns, or deletes a note.
- **Classes.** The two reads are routine and reversible. `errors.resolve` and `errors.unresolve` are routine and reversible: each undoes the other. What Sentry does besides (a notice, a linked ticket that closes) is not undone by the other op, which is why the runbook has a list to check before the ops are turned on. `errors.assign` and `errors.comment` are routine and compensable: no op leaves an issue unassigned again or removes a note, and the member or the followers are told. None is high: each is bounded by the policy, rate-limited, and off until the operator turns it on.
- **A note is not repeat-safe.** Sentry has no idempotency key for a note, and a marker in the text would change what is posted, so a second `Execute` with one execution id posts again. The connector test declares `errors.comment` `NotRepeatable`, as GitHub's `issue.comment` is. chapd does not call `Execute` twice for one execution id.
- **Not verified against Sentry itself.** Nothing here ran against Sentry. The routes, the field names, the `limit` parameter, the `Link` header, `assignedTo` by email address and the scope names are written from the author's knowledge of the API and are exercised only against the fake (`internal/connectors/sentry/sentrytest`). If one differs, the op fails with a fixed sentence and nothing is written. `docs/runbooks/sentry.md` lists them and what to check before turning the ops on.
