# ADR-003: Vault: where Chaperone keeps credentials, and how agents never see them

- **Status:** **Accepted** (operator sign-off). Amended 2026-10-24 for the separate agent account, one-device approval, the phone passkey, the orchestrator token and the critical class for secrets: see "Amendments" at the end.
- **Credentials in scope for Phase 1:** GitHub App private key; Google OAuth refresh token(s) (mail, Drive); the ntfy topic and any notifier token; Chaperone's own keys (interim run-token issuer key, ledger anchor signing key, execution-grant signing key). Later: Notion, Resend, deploy targets, model providers.
- **Incidents this answers:** 19 Oct (a secret key printed into an agent log); and today's reality that agents hold the operator's GitHub token.

## Context

- Before the runner exists, agents used to run as the operator on the server, and anything the operator account can read, an agent can read. **A later decision ends that before Phase 1 ships:** agents run under their own low-privilege Windows account (the "agent account"), the operator account (where the orchestrator, the lead agent also called "the orchestrator", runs) is a third principal, and `svc-chaperone` is the fourth. The vault still cannot live in the operator's DPAPI scope, Credential Manager, or any file the operator account can read, because the operator account also holds the orchestrator token (ADR-007) and any malware running as the operator account is outside the agents' sandbox. Until the accounts are created, the old shared-account situation holds and is a recorded accepted risk (RT-06, RT-07).
- DPAPI (`CryptProtectData`): typically only a user with matching logon credentials can decrypt, and only on the same computer. With the flag `CRYPTPROTECT_LOCAL_MACHINE` **any user on the machine can decrypt**, so that flag is forbidden here. An application-specific `pOptionalEntropy` blob can be supplied. (<https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata>)
- Credential Manager credentials: `CredentialBlobSize` cannot exceed `CRED_MAX_CREDENTIAL_BLOB_SIZE` (5*512 = 2560 bytes) (<https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentiala>). Credentials belong to the logon user, so the same-user problem applies.
- age is a file format with "multiple pluggable recipients"; a file header carries one or more recipient stanzas and a MAC (<https://age-encryption.org/v1>). The Go implementation is `filippo.io/age` v1.3.2 (<https://pkg.go.dev/filippo.io/age>).
- `x/sys/windows` exposes `CryptProtectData` and `CryptUnprotectData`, so DPAPI needs no cgo (<https://pkg.go.dev/golang.org/x/sys/windows>).
- WSL distros belong to the Windows user that registered them `[INFERENCE: standard WSL behaviour, not yet checked on the server]`, so a dedicated service account **cannot** run `wsl -d <pilot distro>`. This shapes the deploy adapter (ADR-004's `chap-host`) but not the vault.

## Decision

**Envelope vault: one age file per secret, with the age identity wrapped by DPAPI under a dedicated service account, plus an offline recovery recipient.**

```
D:\Chaperone\data\vault\<secret_id>.age      one file per secret; ciphertext only
D:\Chaperone\data\vault\index (SQLite)       id, kind, project, owner, fingerprint, created, rotated, last_used
<svc-chaperone profile>\...\vault-identity.dpapi      age X25519 identity, wrapped with CryptProtectData (user scope, own entropy)
offline (operator's safe, never on the server)         recovery age identity (printed / USB)
```

1. **Service account.** `svc-chaperone`, a local standard user (not admin), "Log on as a service" only, no interactive logon, no remote access. `chapd` runs as this account. Its DPAPI master key lives in its own profile, which the operator account (and so any agent) cannot read without an elevated token. Folder ACLs: `D:\Chaperone\data\` full control for `svc-chaperone` and SYSTEM; no access for the operator account, except the read-only ledger export folder (ADR-006). Creating the account and ACLs is a **human-gated, elevated** step; agents never run it.
2. **Encryption.** Every secret is encrypted to two age recipients: the **service recipient** (public half of the identity above) and the **recovery recipient** (public half only is on the server). Losing the server profile, or DPAPI breaking after an account reset, is recoverable by the offline identity; the ciphertext files are safe to include in the existing backup set.
3. **`KeyWrapper` interface.** DPAPI is one implementation (`dpapi-user`). The interface exists so Stage B can swap in a TPM-sealed key, `systemd-creds`, or a cloud KMS without touching the vault format. Phase 1 ships only `dpapi-user`.
4. **Use, never read.** The only internal API is `vault.Use(ctx, id, func(secret []byte) error)`. The secret exists in memory only inside the closure, which belongs to an adapter (GitHub, Google, ntfy, grant signer). **No HTTP route, CLI command or ledger field returns a secret value.** `secrets.*` ops expose metadata only (id, kind, fingerprint, age, last used). Fingerprint = `HMAC-SHA256(vault_fp_key, secret)` truncated, so an agent or log cannot confirm a guessed value.
5. **Import and rotation** go through the console, as a `secrets.write` op: class **critical**, approved with **one device**: Windows Hello on the server or the phone passkey with number matching (ADR-004). The page posts the value straight to `chapd`; the value is never logged, never put in a URL, and the page sets `Cache-Control: no-store`. The GitHub App `.pem` is imported once and the downloaded file is deleted by the operator.
6. **Redaction at every boundary.** One `redact` package, used by the HTTP response writer, the ledger append, the log handler and the CLI's output: (a) exact-match registry of every secret fingerprint's current value in memory; (b) pattern rules for `ghs_`/`ghp_`/`github_pat_` (note the `ghs_` token is now ~520 characters and base64url JWT-shaped; do not use the old 40-character regex; see ADR-002), Anthropic and Google key prefixes, PEM blocks (`-----BEGIN`). A hit replaces the value and raises `REDACTION_BLOCKED` (a denial cause code in the spec) with a ledger event.
7. **Memory and dumps.** Zero secret buffers when the closure returns (best effort in Go). Do **not** depend on Go 1.26's experimental `runtime/secret` (<https://go.dev/doc/go1.26>); revisit when it leaves experiment. Turn off crash dumps for `chapd.exe` `[INFERENCE: via Windows Error Reporting LocalDumps registry settings; how is not yet checked]`.
8. **Canary secrets.** The test suite stores a canary value in the vault, runs every op, and asserts the canary string and its base64/hex forms appear **nowhere**: not in responses, ledger rows, JSONL exports, logs, `chap` output, panic traces, or the SQLite file. This is the regression test for the 19 Oct incident.

## What this does and does not defend (honest limits)

| Attacker | Result |
| --- | --- |
| Agent as the agent account, normal (non-elevated) token | Cannot read `svc-chaperone`'s profile DPAPI master key, the identity file, the vault folder, `chapd`'s memory, or the operator's profile (where the orchestrator token file lives). Can still call `chapd`'s API with its run token, which is the point. |
| Anything running as the operator account | Cannot read the vault or `state.db` either (the ACLs above exclude the operator account), but can read the orchestrator token file (ADR-007) and ask `chapd` for whatever that token's scope allows. High-impact asks still need an approval. |
| Agent that obtains an **elevated** token | Can read everything. Mitigation is UAC prompts on the secure desktop (`[INFERENCE: UAC is at its default on the server; not checked]`), and the house rule that agents run no elevated command. |
| Someone with the disk image, offline | Needs the `svc-chaperone` profile's master key (derived from that account's password); BitLocker on `D:` and `C:` is recommended `[INFERENCE: BitLocker status unknown]`. |
| Malware running **as `svc-chaperone`** (i.e. a bug in `chapd`) | Full access. Mitigation is the small dependency allowlist (ADR-001) and no code loading. |
| Loss of the server profile or reset of `svc-chaperone` | Recover with the offline identity; re-wrap with a new DPAPI identity. See the [vault recovery runbook](../runbooks/vault-recovery.md). |

## Alternatives

| Option | For | Against | Verdict |
| --- | --- | --- | --- |
| **age files + DPAPI-wrapped identity + offline recovery recipient** | Standard, reviewed format; multi-recipient gives recovery; Windows-bound part is one small interface; secrets are plain files so backup and restore are trivial; no extra service. | Two layers to explain; DPAPI binds to one account and machine; needs the service account. | **Chosen** |
| DPAPI only (one `CryptProtectData` blob per secret) | Simplest. | No recovery path; format is Windows-only and undocumented to other tools; Stage B would re-key everything. | Rejected |
| Windows Credential Manager | Built in. | 2,560-byte limit per credential (a 2048-bit RSA PEM is near it; a larger key or a JSON token set will not fit); same-user scope; no recovery; harder to back up. | Rejected |
| Embedded KMS / secrets server (OpenBao / Vault transit, cloud KMS) | Audit, leases, rotation, transit without exposing keys. | A second service with unseal or cloud-KMS dependence (auto-unseal needs a root of trust we do not yet have on one server); ~10 secrets do not justify it; not evaluated in depth `[INFERENCE]`. | Revisit at Stage B or with more than one approver |
| TPM-sealed key (CNG Platform Crypto Provider) | Non-exportable key; strongest at rest. | Harder from Go under a service account; hardware-bound with no recovery by itself; I could not fetch Microsoft's current provider doc (404), so the details are unverified. | Planned as a second `KeyWrapper` |

## Verify

- Vault: round-trip test; wrong-account decrypt fails (Windows CI job); recovery-identity decrypt works; fingerprint never reveals value; `Use` closure leaves no copy in returned errors.
- The canary-secret test above, and a test that the `chap` process can never print a secret even if `chapd` is told to (the API has no such route).

## Amendments (2026-10-24, first build)

**Amendment 1. Account split.** The human step that creates accounts now creates two accounts, `svc-chaperone` and the agent account, and a reviewed script launches the factory's agents under the second one. Every "agent as the operator account" statement above is superseded by the row for the agent account. The operator account remains excluded from the vault folder and `state.db`.

**Amendment 2. `secrets.*` is critical.** `secrets.write` (import, rotate) and any later `secrets.*` op are class critical: never auto-allowed, always an approval card bound to the exact op hash, logged loudly (an alert on every approval and every use). `secrets.*` ops still expose metadata only; no op returns a value.

**Amendment 3. One device.** Approving a `secrets.*` op does not need two devices. The compensating controls are the ones already here: the card is rendered by the server and its hash is in the challenge, the console binds `Host` and `Origin`, and nothing a request can carry is a secret value.

**Amendment 4. Accepted residual risk: split or re-encoded secrets (RT-25).** The redactor (section 6) masks a registered secret's raw bytes and the forms the registry derives from it (standard, raw, URL-safe and raw-URL base64, lower- and upper-case hex, the JSON-escaped text, and a CRLF/LF swap), plus the pattern rules. It does **not** find a secret that was cut into pieces (`ghp_abc` + `def...` sent as two params, or one character per line), or that was transformed by anything else (rot13, reversed, gzip then base64, URL-encoding with percent escapes, a character per request, a cipher the sender holds the key to). Matching those needs the secret to be re-derived by the same transform, and no filter can list every transform. We accept this because an agent that can send those pieces already holds the secret; the redactor exists to stop `chapd` and `chap` from **echoing or storing** a secret, which is what the 19 Oct incident was, and it blocks that. What bounds the damage: the agent account cannot read the vault, `state.db` or the key files (the table above); every high-impact op is approved on a card that shows the exact params (ADR-004); the ledger redacts every event as it is written; and the canary suite fails the build if any registered form shows up. Revisit with entropy or length-based detection when a real case shows the need; it will add false positives to ordinary params.

**Amendment 5. The Linear intake: a second service credential in the vault.** `chapd` holds two more vault secrets, `linear-client-id` and `linear-client-secret` (kind `linear-oauth-client`; a vault id takes no dot), the client of a Linear OAuth app with client credentials enabled. They are read through `Vault.Use` only, to ask Linear's token endpoint (`grant_type=client_credentials`, HTTP Basic, scope `read,write`) for a bearer token. The token is held the way ADR-002 holds GitHub tokens (never written anywhere) and capped in time: it lives in `chapd`'s memory only, for at most one hour although Linear issues it for 30 days, is replaced after a 401, is registered with the redaction registry while held, and is never in a log line, a ledger event or an op result (`internal/connectors/linear/token.go`; tests: `TestTokenIsNeverKeptLongerThanTheCap`, `TestACallRefetchesTheTokenAfter401`, `TestTheTokenIsRegisteredForRedaction`, and the ledger scan in `cmd/chapd` `TestIntakeAllowedOpsAreLedgered`). Four ops use it (`intake.list`, `intake.comment`, `intake.move`, `intake.states`), all class routine, orchestrator token only, and off in the baseline until a policy PR turns them on.
- **Why `write`.** Linear has no scope that moves an issue to a state and does nothing else (`comments:create` and `issues:create` do not cover a state change), so the app holds `write`, which reaches the whole workspace. The guard is Chaperone's policy, not the app: the project file's `linear:` block names **one team key, one label and the state names `intake.move` may set** (`internal/policy/linear.go`); `chapd` sends **five fixed GraphQL documents** and the caller supplies no query, no team, no label and no state id; a write is allowed only on an item of that team that carries the label **at the moment of the write** (read in `Check`, and again in `Execute` with the token that writes); the Engineering team is refused by key and by name; and the mutations carry only the fields they need (a comment: id, issue, body; a move: the state id), so no label, title, description, assignee, archive or delete change can be sent. The operator's amendment is enforced as written: **the `claude` label is never removed.** A team restriction on the app is used as well when the plan offers it (runbook step 1); the policy does not depend on it.
- **The residual window.** Linear has no conditional update, so the label can change in the milliseconds between the second read and Linear's answer. A write in that window lands on an item that has just lost the label. Accepted: the writes are a comment and a state move on the operator's own board, both reversible by a person.
- **Reads.** `intake.list` returns the open items with state, title, description, comments (at most 8), links and update time, from a cache that a poller refreshes every 15 minutes (`-linear-poll-interval`; `intake.list refresh` reads at once, at most every 30 s per board). Board text is untrusted data: it is cleaned, capped, flagged `untrusted_text`, and an item whose text looks like a secret is withheld. The cache is memory only.
- **Rate limits.** The policy pack's `rate_per_minute` per caller and op, a budget of 300 Linear calls in any 60 minutes in `chapd`, and a stop on Linear's own signals (429, `RATELIMITED`, 20 or fewer requests remaining) until the time Linear names.
- **Writes are sent once.** A definite refusal by Linear is `failed`; an answer that does not show whether Linear acted leaves the op `unconfirmed` and names the comment id (derived from the execution id) so the comment can be looked up.
- **A fix found on the way.** The redaction registry now also masks the **trimmed** form of a value that was saved with trailing white space (a console paste or an editor adds a newline; the connector uses the trimmed value, so only the trimmed form shows up in a comment or a log). Before this, such a secret passed the redactor when it appeared without its newline (`internal/redact/registry.go`, `TestExactValueSavedWithTrailingWhitespaceIsMaskedWithoutIt`). Amendment 4's list of derived forms gains this one.
- **Not decided here.** Whether the orchestrator's pickup comment must be a fixed template (it is free text up to 4 000 bytes today); a webhook instead of polling (needs a public HTTPS endpoint, ADR-004 rejects one for phase 1).
