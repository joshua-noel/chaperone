# ADR-004: Approvals: Windows Hello or phone passkey, push as a wake-up, and push-bombing defences

- **Status:** **Accepted** (operator sign-off). Amendments 14 (the service also holds `[::1]`) and 15 (security keys and phones, opt in) are dated 19 Nov 2026. **Amended 2026-10-24** for one device for every class, no quiet hours or daily budget, the phone approving from Phase 1, and the critical class: see "Amendments" at the end. The text below is the amended text; the first draft said "server only, phone notify-only, `approve2` later".
- **Inputs:** the maintainers' design decision ("Server console (Windows Hello) + phone push. The exact action is shown on both; no batching across different actions"); factory-spec v0 `operation-request.schema.json`, `operation-approval.schema.json` (approval binds `op_hash`, `request_id`, `run_id`; has `nonce` "folded into the authenticator challenge"; `shown.display_sha256`; `confirmations[].channel` is `pc` or `phone`; "which confirmations suffice (one channel or both) is policy, not schema"); denial codes `OP_APPROVAL_REQUIRED/DENIED/EXPIRED`, `APPROVAL_HASH_MISMATCH`, `APPROVAL_CONSUMED`; stop code `APPROVAL_FLOOD`.

## Context

- A WebAuthn assertion with **user verification** is proof that the person at the server unlocked the Windows Hello key (PIN or biometric). A script running as the same Windows user cannot produce it. That is the property agents-as-operator cannot fake.
- WebAuthn requires a secure context, but the spec explicitly makes **`http://localhost` a valid origin** and `localhost` a valid RP ID (<https://www.w3.org/TR/webauthn-3/>, "Validating the origin"). So the console at `http://localhost:55398` can use Windows Hello with no certificate.
- The spec says challenges "MUST be randomly generated by Relying Parties in an environment they trust" and should be stored server-side (WebAuthn L3 §13.4.3). So the challenge cannot *be* the op hash; it must contain fresh randomness, and the server keeps the mapping challenge → approval.
- **Push-bombing is a real attack.** Uber's 2022 breach started with MFA fatigue (<https://www.uber.com/us/en/newsroom/security-update/>, summarised at <https://www.infoq.com/news/2022/09/Uber-breach-mfa-fatigue/>). CISA's guidance: if you must use push MFA, use **number matching**; phishing-resistant MFA (FIDO/WebAuthn) is not subject to push bombing (<https://www.cisa.gov/sites/default/files/publications/fact-sheet-implement-number-matching-in-mfa-applications-508c.pdf>, <https://cisa.gov/sites/default/files/publications/fact-sheet-implementing-phishing-resistant-mfa-508c.pdf>). Microsoft's number matching shows a number on the sign-in screen that the user must enter in the app (<https://learn.microsoft.com/en-us/entra/identity/authentication/how-to-mfa-number-match>).
- **A toast cannot come from a Windows service.** All services run in session 0 and any UI they show is visible only to whoever is connected to session 0 (<https://learn.microsoft.com/en-us/windows/win32/services/interactive-services>). The existing `alerts.ps1` toast works because its scheduled task runs "only when user is logged on". Chaperone needs the same: a helper in the operator's session.
- **A phone cannot reach `localhost` on the server.** Any phone-side *approve* needs a remote path. Tailscale Serve shares a local service within the tailnet (<https://tailscale.com/kb/1242/tailscale-serve>); the Personal plan is free (up to 6 users; <https://tailscale.com/pricing>); HTTPS certificates publish the machine and tailnet name to the public Certificate Transparency log (<https://tailscale.com/kb/1153/enabling-https>).

## Decision

### 1. What "approve" is

**The approve is a WebAuthn assertion (user verification required) made on an approval card by one of two devices: Windows Hello on the server (console card), or the phone passkey with number matching (phone page, section 5).** One device is enough for every class, critical included. There is no Approve button in any notification.

- Server: RP ID `localhost`, origin `http://localhost:55398`. Phone: RP ID `<server>.<tailnet>.ts.net`, origin `https://<server>.<tailnet>.ts.net` (section 5). The console server checks `Host` and `Origin` on every request on both origins (DNS-rebinding defence) and uses `SameSite=Strict`, `HttpOnly` cookies.
- Credentials are created with `authenticatorAttachment: platform`, `userVerification: required`, attestation `none` (a Windows Hello key on the server, a passkey on the phone). The server stores `rp_id` and `origin` per credential from day one. **Amendment 15 makes the attachment a per-install setting:** `platform` stays the default, `any` also allows a security key and a phone through the cross-device prompt; user verification stays required for both.
- **Challenge** = `base64url( SHA-256( JCS{ approval_id, nonce, op_hash, request_id, display_sha256 } ) )`. `nonce` is 128+ random bits (spec: `^[A-Za-z0-9_-]{22,64}$`), so the challenge is unpredictable as WebAuthn requires, and the signature covers the op hash, the request, **and the hash of the exact card text that was shown**. The server stores `(challenge → approval_id)`; the assertion (`authenticatorData`, `clientDataJSON`, signature) is kept next to the ledger, and the approval record carries `assertion_sha256` (spec field).
- Server checks: signature against the stored credential; `UV` flag set; `clientDataJSON.origin` and `rpIdHash` match; challenge equals the stored one and unused; approval not expired; **op hash recomputed from the stored request equals the approved hash** (`APPROVAL_HASH_MISMATCH` otherwise). Do not treat a zero signature counter as a clone signal (platform authenticators may report 0 `[INFERENCE]`).
- **Single use.** `pending → approved` is a compare-and-set in SQLite; `approved → executing` is another, done in the same transaction that writes the ledger event. A second use gets `APPROVAL_CONSUMED`. The approval is valid for 5 minutes after the decision; the request itself for 30 minutes (15 for `deploy`), then `OP_APPROVAL_EXPIRED`.
- **Registration.** The first approver is enrolled by an elevated `chapd enroll` run by the operator (human-gated; see amendment 7). After that, enrolling another credential or device is itself an op, `approvers.enroll`, tier `approve`. The `approvers` table supports many approvers, each with per-project and per-op scopes (multi-approver from day one).
- **Library:** `github.com/go-webauthn/webauthn` v0.18.2 (pre-1.0; the build starts with a spike that registers and asserts against real Windows Hello in Edge before anything is built on it).

### 2. Tiers

| Tier | Confirmations required | Phase 1 ops |
| --- | --- | --- |
| `auto` | none (policy checks only) | `pr.open`, `pr.update`, `pr.merge` of a **low-tier** PR (ADR-002 step 5), `branch.push`, `health`, `logs` |
| `approve` | **one device**: Hello on the server **or** phone passkey with number matching | high class: `deploy`, `mail.send`, `drive.share`, `data.apply`, `pr.merge` of a medium or high-tier PR, `pr.push.workflow`. Critical class (amendment 4 and the spec's `approver.add`, `policy.activate`): `secrets.*` (`secrets.write`), `repo.settings`, `host.scripts.refresh`, `approvers.enroll` |

The tier `approve2` (two devices) is **retired** (amendment 1). **Critical** is a class label, not a different ceremony: the card is marked CRITICAL, an alert is raised on request, approval and execution ("logged loudly", spec), and the op stays disabled in the catalog until its adapter exists and a policy PR enables it. Which ops are enabled is policy data, so nothing in this table turns an op on.

A phone approval needs number matching and the card shown on the phone; a notification alone never approves anything. The card is never batched: one approval, one request, one op hash (spec).

### 3. The card shows the exact action

A per-op template renders the card; `display_sha256` is the hash of that rendered text and goes into the challenge. Templates:

- `deploy`: target, full SHA, commit list from the currently deployed SHA, policy checks passed (verify green on that SHA, load gate `normal`, backup age and "verified", migrations in the diff).
- `mail.send`: from account, every recipient, subject, the **full rendered body**, attachment names and SHA-256s.
- `drive.share`: file name and id, recipients, role, link visibility.
- `pr.merge` (medium or high-tier PR): PR, head SHA, risk tier and the paths that set it, the diff stat; for the high tier also the diff itself, with workflow files listed first.
- Cards also show who asked (run id, profile, brief title, or `orchestrator`), the agent's `reason` (marked untrusted), policy version, expiry.

### 4. The phone

**Notifier interface** with one Phase 1 driver, **ntfy**, and a documented second driver, Pushover. **The push only wakes the phone**: it carries no authority and no parameters. The phone approves by opening the console page over the tailnet (section 5).

Push content: op kind, project, first 8 hex characters of the op hash, expiry time, count of pending approvals. **No parameters, no recipients, no body text, no link, no action buttons.** The operator opens the console from a bookmark on the phone or the server. A forged push (leaked topic) therefore cannot phish a link or leak content.

`shown.channels` includes `phone` when the phone's console page rendered the card (the server saw the request) and the notifier API accepted the wake-up message; ntfy gives no delivery receipt, so the push proves *publication*, not display (note for the spec authors: say this in the field description).

**Decision:** Phase 1 uses **ntfy.sh with a 128-bit random topic** and the minimal payload above, behind the `Notifier` interface. Reasons: no infrastructure, free, open source (self-hosting is a base-URL change), and because the push carries no authority, its worst failures are a missed wake-up (the console and toast still work) or spam. The approve itself is the phone passkey in the last column of the table, reached over Tailscale Serve (section 5). Pushover is the second driver if the operator wants delivery receipts and repeat-until-acknowledged for `deploy` (one small extra change).

### 5. Phone passkey with number matching (Phase 1)

Reachable only on the tailnet: `chap-console` is also served by `tailscale serve` at `https://<server>.<tailnet>.ts.net`, a **second RP ID** (`<server>.<tailnet>.ts.net`). The phone registers its own passkey there (enrolment is an `approvers.enroll` op, approved from the server). For every approve-tier request the phone may approve it alone:

1. The server console card shows a two-digit number. The phone page shows the same card text (rendered by the server, so a compromised server browser cannot change it) and **three** numbers; the approver taps the one on the server screen. A wrong choice denies the request and counts toward the cooldown in section 6.
2. The phone then makes a passkey assertion whose challenge is built exactly as in section 1 (its own `nonce`). That one assertion approves.

Why number matching: it shows the person is looking at the server screen where the request surfaced, so a blind tap on a phone page cannot approve (CISA's number-matching guidance). The phone card is a second, server-rendered display of the same text, so a hostile console browser that shows a different card from the one signed is still visible to a phone approver. WebAuthn binds the assertion to the origin, so a look-alike page cannot collect a usable assertion. Cost: a tailnet node on the server and phone, and the CT-log-visible machine name.

**Design choice to confirm (not in the decisions):** the number is shown on the server, so a phone approval still needs the operator to see the server console or its toast. If the operator wants to approve with the server off or out of sight, the number would have to travel another way; that is a new decision, not something this ADR assumes.

### 6. Push-bombing and approval-fatigue defences (all in Phase 1)

1. **No approve from a notification** (above). Nothing a push can do accepts anything. CISA states phishing-resistant MFA is not subject to push bombing; we get that property by making the approve a WebAuthn ceremony the operator starts himself, from the card on the server or from the phone page he opens.
2. **Exact op shown** (§3), `display_sha256` signed into the challenge.
3. **Deduplication.** A request with an `op_hash` that is already pending returns the same pending approval and sends **no second push**.
4. **Caps** (policy values, the defaults): at most 2 pending approvals per run, 5 per project, 10 in total. They bound what **agents** can queue; they never limit how many approvals the operator may make (there is no daily budget). Beyond a cap the request is refused and a stop signal `APPROVAL_FLOOD` is raised for the run (stop-table code). There is no push-rate cap: dedupe (item 3) and these caps already bound the pushes, and the earlier "6 pushes per hour" coalescing is removed because it limited the operator's notifications.
5. **Sticky deny / cooldown.** After a denial or expiry of an op hash, the same op hash is refused for 60 minutes (`OP_APPROVAL_DENIED`). Re-asking with trivially changed parameters is caught by per-run caps and by the `THRASH` counter.
6. **A passkey prompt is only ever started by the operator's own click**: on a card in the console, or on the phone page he opened. Chaperone never opens a prompt on its own.
7. **No quiet hours and no daily approval budget.** Push priority never drops by time of day and requests keep their full expiry. Nothing in Chaperone limits how many approvals the operator makes or when.
8. **Measure it, limit nothing.** The ledger gives approvals per day, time-to-decision and denial rate (design principle: "Respect for humanity"). These are reports; no value feeds a limit.
9. **Number matching** for phone approvals (section 5).

## Alternatives not chosen (short)

- **Approve by tapping a push action (ntfy http action, Pushover acknowledge).** Exactly the push-bombing shape. Rejected: authority must not ride on a tap.
- **TOTP or SMS codes.** Phishable; no binding to the op. Rejected.
- **Windows Hello without a browser** (call `webauthn.dll` from Go). No console page means no card text beside the prompt, and the operator's click-from-card habit is lost. Not pursued `[INFERENCE: the native API was not evaluated]`.
- **Secure Payment Confirmation** (browser-rendered transaction text). A payments-specific browser feature `[INFERENCE: not evaluated for this use]`.

## Verify

- Approvals: approve deploy A, request deploy B with another SHA: `APPROVAL_HASH_MISMATCH`; reuse a consumed approval: `APPROVAL_CONSUMED`; expired: `OP_APPROVAL_EXPIRED`; assertion for another request: refused; the agent's own run token, and the orchestrator's token, cannot approve their own requests (`POLICY_BREACH`); flood: 3rd pending request from one run refused with `APPROVAL_FLOOD`; a critical-class op is approved by one device and raises its alert.
- Notifications: push body contains no param text (golden test); no URL, no actions; no quiet-hours or push-rate logic exists.
- Console: real Windows Hello registration and assertion in Edge against `http://localhost:55398`.
- Phone: an approve-tier op is approved by the phone alone; a wrong number denies and starts the cooldown; the phone card text equals the server card text (hash); a look-alike origin collects no valid assertion (WebAuthn origin binding test).

### Interpretations and accepted risks to confirm

1. **Reading of the decision to drop limits on the operator.** The decision says dedupe, sticky deny and "no approve from push text" stay and that limits on the operator go. I kept the agent-facing pending caps (without them RT-15 and `APPROVAL_FLOOD` have nothing to test) and removed the push-rate coalescing. If the operator wants the 6-per-hour coalescing back, it is one policy value.
2. **Number display for a phone-only approval** (section 5): shown on the server.
3. **Accepted risk from one device being enough.** The first draft used the phone as a second display so that a hostile console browser could not show one card and sign another. With one device enough, a Hello on the server approval has no second display. Controls that remain: the card is rendered by the server, `display_sha256` is in the challenge, `Host`/`Origin` checks, and the ledger keeps the assertion. To be recorded in the threat model as an accepted risk with an owner and a date.

## Amendments (2026-10-24, console and sign-in)

### Amendment 6. The phone credential: how the phone reaches the console (design for the phone; to confirm)

**Question.** Section 5 says the phone registers a passkey at a second RP ID and origin. The phone cannot reach `http://localhost:55398`, and a WebAuthn credential is bound to the RP ID of the page that made it, so *how the phone reaches the console decides the RP ID, the origin, the TLS story, who else can reach the page, and what a lost credential costs*. The console build covers only the part that does not depend on the answer: `internal/console` takes a list of `Origin{RPID, URL}`, the guard accepts exactly those hosts, every credential row stores `rp_id` and `origin`, and a credential is only accepted at the origin it was made at (tested with the server origin and a second `https://` origin). Nothing below is built yet.

| Option | RP ID and origin | TLS | Who can reach the page | Phone must be | Verdict |
| --- | --- | --- | --- | --- | --- |
| **A. Tailscale Serve (tailnet only)** | `<server>.<tailnet>.ts.net`, `https://<server>.<tailnet>.ts.net` | Public-CA certificate that `tailscaled` provisions and terminates; no private CA on the phone | Only tailnet devices the ACL allows | On the tailnet (Tailscale app connected), anywhere in the world | **Recommended** |
| B. LAN direct (HTTPS on the server's LAN address) | A LAN name (`server.lan`, `server.local`) | No public CA issues for those names, so a **private CA** must be installed and trusted on the phone; a trusted private CA is a standing MITM key for that phone | Every device on the LAN (Wi-Fi guests, IoT) once a firewall rule opens the port | On the home Wi-Fi only | Rejected: worst trust cost, narrowest use, widest exposure |
| C. Public tunnel (Tailscale Funnel, Cloudflare Tunnel) | A public name | Public CA; with a Cloudflare tunnel the provider terminates TLS | The whole internet | Anywhere, no VPN app | Rejected for Phase 1: the sign-in and enrolment endpoints and the HTML parser face the internet, and the card text passes a third party that can alter it |
| D. Phone as a roaming authenticator for the server page (hybrid/caBLE: the server's browser at `localhost` shows a QR, phone makes the passkey for RP ID `localhost`) `[INFERENCE: not tried]` | `localhost`, `http://localhost:55398` (same as the server) | none new | server only | Near the server (Bluetooth) | Fallback only. The card stays on the server screen, so the phone is not an independent display and the point of a second, independent display is lost. `internal/console` refuses a registration whose reported attachment is not `platform` unless the operator sets `-approver-authenticators any` (amendment 15), so D needs that setting |

**Recommendation: A.** Concretely:

1. **Names.** RP ID = the full MagicDNS name of the server (`<server>.<tailnet>.ts.net`), origin `https://` + that name, no port (Serve's default 443). Use the full name, not the tailnet suffix, so a credential is valid for exactly this machine. Renaming the server or the tailnet invalidates the passkey: re-enrol (the `rp_id` column makes the stale rows visible; revoke them).
2. **Listener.** Chaperone keeps listening on `127.0.0.1:55398` only. `tailscale serve --bg --https=443 http://127.0.0.1:55398` makes `tailscaled` terminate TLS and proxy to loopback (the Serve docs say only `http://127.0.0.1` targets are supported for proxies: <https://tailscale.com/docs/reference/tailscale-cli/serve>). `chap doctor` checks that nothing but loopback is bound and that `tailscale serve status` lists exactly that one mapping. The console then sees plain HTTP from a local process: it identifies the phone origin by the `Host` header, so `Config.Origins` has two entries and the guard needs no proxy-header trust. `[INFERENCE: that Serve forwards the original Host header unchanged; verify when the phone is set up. If it does not, the phone work adds a configured Host alias for that origin.]` The `Host`/`Origin` check is not authentication: any local process can send `Host: <server>.<tailnet>.ts.net` to loopback. The authentication is the assertion.
3. **Enrolment.** `approvers.enroll` (critical class) is approved on the server. Approving it calls `console.IssueEnrollment(ctx, db, &approverID, ttl, now)` (built with the console) and the server card shows the one-time address `https://<server>.<tailnet>.ts.net/enroll#<token>` as text and as a QR code on the server screen, so the token reaches the phone over the camera, not over ntfy or any third party. (A QR encoder is not in the standard library: the phone work either writes the few hundred lines or adds a module to the allowlist; typing the address is the fallback.) Token: 128 bits, hash only in the database, 10 minutes, single use, bound to the approver id; it sits in the URL fragment so it never reaches a server log. The phone then runs the same ceremony as the server (platform, discoverable, UV required, attestation none) and the credential row gets the phone's `rp_id` and `origin`.
4. **Tailnet policy (operator).** Tag the server and the phone and write an ACL that allows only `phone -> server:443`. Without it every node on the tailnet can reach the sign-in page. Serve is not Funnel: nothing is public. Keep key expiry in mind: a phone whose node key has expired silently loses the tailnet (Tailscale's default is 180 days `[INFERENCE: not re-checked]`).
5. **Who may change `tailscale serve`.** Whoever can rewrite the Serve mapping can point the phone origin at another local server and relay the real console while altering the card text. The assertion still covers the real `display_sha256`, so the approver would approve text he did not see; number matching (the server shows the number) and the server card are the controls that remain. The install setup should restrict the Tailscale operator to the operator's elevated account and keep the agent account out of Tailscale's local API `[INFERENCE: how Tailscale on Windows scopes this is not verified]`.

**Trade-offs to flag to the operator.**

- **Synced passkeys.** A phone passkey is normally a *synced* credential (iCloud Keychain, Google Password Manager): backup-eligible, and recoverable from the provider account. The Hello credential on the server is device-bound `[INFERENCE: not measured here]`. So the phone adds "Apple or Google account takeover" to the ways to obtain a signing key. What still stands in the way: the attacker needs a tailnet node that the ACL lets reach the server, user verification on the phone, and (for approve) the number on the server screen. The console stores `backup_eligible` and `backup_state` for every credential, so a policy can later forbid BE=1 credentials; turning that on now would lock out iPhones.
- **Certificate Transparency.** The `ts.net` certificate publishes `<server>.<tailnet>.ts.net` in public CT logs (Tailscale HTTPS docs, already cited in "Context").
- **Availability.** If the phone or the server is off the tailnet, the phone cannot approve; the server's Hello still can (one device suffices). Nothing falls back to a weaker path.
- **Tailscale as a dependency.** Traffic is end-to-end encrypted and the certificate is terminated on the server; Tailscale still sees who connects to whom, and its client runs as a privileged service on the server. That is new host trust, accepted by the operator.
- **Revoking a device.** `credentials.revoked_at` is honoured by sign-in today; the button is a later change, and the runbook must say "revoke the phone credential, then remove the node from the tailnet".

**What the phone work adds on top of the console build:** the second `Origin` from configuration, the enrolment card and QR, number matching, the phone card page, `chap doctor` checks, and RT-18/RT-19. What it must not change: `rp_id`/`origin` per credential, the Host/Origin guard, the CSRF scheme, single-use ceremonies.

### Amendment 7. The console as built, and the Hello check

**Built.** `internal/console` (guard, sessions, WebAuthn ceremonies, `chapd enroll` body), `web/` (templates, vendored htmx 2.0.11 and Basecoat 1.0.2, SHA-256 pinned in `web/web.go` and checked by `go test ./web/`), migration `0002_console_approvers.sql` (`approvers`, `credentials`, `console_sessions`, `console_ceremonies`, `console_enrollments`), and `chapd enroll`. Decisions made while building:

- **Discoverable (passkey) sign-in.** The picker names the credential, so the server reveals nothing about who is enrolled before an assertion. Registration therefore requires a resident key.
- **Refusals are explicit in code, not only in the library.** The server checks the UV and UP flags itself as well as through `go-webauthn`, and refuses a regressed non-zero signature counter (`clone_warning`). A counter that stays 0 is fine (platform authenticators may report 0, see section 1).
- **A ceremony is single use and burns on any attempt.** Finish deletes the row before it reads the response, so a replay, a retry and a wrong guess all find nothing. It is also bound to the browser's CSRF cookie, so a stolen ceremony id from another browser is refused.
- **Sessions are weak authority by design.** A session (30 minutes idle, 8 hours absolute, hash-only in the database) lets the operator browse. It approves nothing: the approve in amendment 8 needs a fresh assertion over the approval challenge. Browsers send cookies to every port on the same host name, so another local web server at `localhost:<other port>` receives `chap_session`; this is why the session must never be enough to approve.
- **First enrolment only through `chapd enroll`.** The command refuses when an approver exists. Adding a device is `approvers.enroll` (amendments 8 and 9), which calls `IssueEnrollment` with an approver id.
- **Events.** `Config.OnEvent` receives `console.enrolled`, `console.login` and `console.refused` (with a reason code). The ledger subscribes later; until then the events only reach `chapd enroll`'s output and the tests.

**The one-command Hello check (needs the operator at the server).**

1. In PowerShell with the Go toolchain on the PATH (README, "Developing"), from the merged Chaperone checkout. `-scratch` keeps everything in `%LOCALAPPDATA%\Chaperone-h3\` (created if missing) so no admin rights and no ACLs are involved; the real `state.db` is created by the install script, and `chapd enroll` is run elevated against it then:

   ```powershell
   $env:CGO_ENABLED='0'; go build -trimpath -o dist\windows\ ./cmd/chapd
   .\dist\windows\chapd.exe enroll -scratch
   ```

   Port 55398 must be free (nothing else uses it). The command stays running and prints what to do next.
2. The command prints `http://localhost:55398/enroll#<token>`. Open that address in **Microsoft Edge** on the server (the token is one use, 10 minutes). Click **Create passkey** and approve with the Windows Hello PIN, fingerprint or face.
3. The command prints `OK console.enrolled credential_id=... rp_id=localhost origin=http://localhost:55398 uv=true ...` and then asks for the sign-in. Open `http://localhost:55398/login`, click **Sign in with a passkey**, approve again.
4. The command prints `OK console.login ... uv=true sign_count=N` and exits 0. The page shows "Signed in as operator".
5. Paste the two `OK` lines into the pull request as the evidence (they are not secrets: a credential id and public facts). To repeat only the sign-in later: `.\dist\windows\chapd.exe enroll -check -scratch`. To start over: delete `%LOCALAPPDATA%\Chaperone-h3`.

What the two `OK` lines prove: the browser created a platform credential at RP ID `localhost`, the server verified the attestation's UV flag (`uv=true`), and a later assertion signed by that credential verified with the UV flag set. If Edge or Windows Hello refuses, or the command prints `REFUSED reason=...`, send the whole output to the orchestrator: that is the "Flip condition" evidence ADR-001 asks for.

## Amendments (2026-10-24, approvals engine)

### Amendment 8. The approvals engine as built

**Built.** `internal/approvals` (engine, card templates, migration `0006_approvals.sql`) and `internal/console/approvals*` (the `/approvals` screen, the assertion verifier). Decisions made while building, none of which changes sections 1 to 6:

- **What the challenge fixes.** `spec.ApprovalChallenge` binds `approval_id`, `request_id`, `run_id`, `op_hash`, `decision`, `approver.id`, `nonce`, `expires_at`, `policy_version` and `display_sha256` (the spec's list, a superset of the first draft's). So the approver and the decision are fixed before the operator is asked, and `expires_at` has to be fixed then too. **`expires_at` = the moment the challenge is made + 2 minutes (the time to answer it) + 5 minutes.** An approval is therefore valid for at least 5 and at most 7 minutes after the decision; the "5 minutes" of section 1 is the lower bound. A challenge unanswered for 2 minutes is dead.
- **Several challenges per card.** Each "Approve" click makes its own challenge (own nonce); the answer takes it (delete before read) and a second answer, a retry or a wrong guess finds nothing. A challenge is also bound to the browser's csrf cookie, to the console origin and to the approver, and the final compare-and-set is `UPDATE ... WHERE state = 'pending'`. Ten concurrent answers for one card: one wins, nine get `APPROVAL_CONSUMED`.
- **A fresh assertion, never the session.** The console session only lets the operator look and deny. `Console.VerifyAssertion` is the login check with the library's random challenge replaced by the approval's: UV and UP checked twice, credential must be the approver's and be registered at the origin the request arrived on, a regressed counter is refused, and it never reads the session.
- **Deny needs no assertion.** It only removes authority, so a signed-in session with CSRF is enough. The denial record still carries a challenge hash (the schema requires it); `confirmations` is empty.
- **Self-approval.** Every decision entry point takes an `Actor`; anything but a console approver is `POLICY_BREACH` (and asks the caller to raise that stop). The console treats a request with an `Authorization` or `Proxy-Authorization` header as a token's, whatever cookie rides along.
- **The card is re-derived.** At begin and at approve the engine re-hashes the stored request (must equal the approved `op_hash`: `APPROVAL_HASH_MISMATCH`) and re-renders the card from the stored request, checks, evidence, class, policy version and expiry (must equal the stored text and `display_sha256`: `DISPLAY_MISMATCH`). The first line of every card is `CHAPERONE APPROVAL CARD v1`; a template change bumps the version and a pending card from the old version cannot be approved (it expires and is asked again). Triggers in the migration make a stored card, request and state machine immutable by accident; they do not stop an attacker with file access, who would also have to forge the ledger.
- **What a card shows.** A per-op template lists the fields it knows first, then every other parameter under "Other parameters", so nothing can be left off. Untrusted text (the reason, evidence, parameters) is escaped: control, bidi, zero-width and no-break-space characters become visible `\u{...}` escapes, identifiers (addresses, SHAs, refs) are printable ASCII only so a look-alike letter shows up as an escape, and multi-line text is shown with a `    | ` prefix on every line so none of it can pass for a line of the card. The page puts the text in a `<pre>`; the page's script hashes `textContent` and compares it with `display_sha256` before it asks for a challenge, and the end-to-end test does the same with the served HTML. A card larger than 512 KiB is refused: text that cannot be shown whole cannot be approved.
- **Sticky deny is the operator's "no".** It starts from a denial, or from the expiry of a card nobody answered. A cancellation (the requester withdrew, the run ended) and an approval that went unused do not start it.
- **Caps** count live pending cards: per requester (a run, or the orchestrator), per project, in total. The flood refusal is `OP_POLICY_REFUSED` with `Stop = APPROVAL_FLOOD`; the engine asks the caller's `Config.Stop` hook (inside the transaction) to raise it.
- **Ledger.** The engine appends `op.approve` (decision `approved` or `denied`, including cancellations with approver `chaperone`) through an `approvals.Ledger` interface in the caller's transaction, so the caller adapts the ledger's `AppendTx`. The spec closes the attributes of `op.approve`, so `assertion_sha256`, `display_sha256` and `challenge_sha256` travel in the event `body`; the full evidence is `approval_assertions` (the assertion as received) and `approvals.record_json` (the spec `operation-approval`, validated against the schema before it is stored). `approver.id` is the lower-cased approver name (`operator`), or `approver-<row>` when the name leaves nothing usable.
- **Only the `pc` channel counts** until amendment 9 adds number matching (`Config.Channels`). An assertion made at the phone origin verifies and is then refused as `channel_not_enabled`; `shown.channels` is therefore `["pc"]` and the wake-up push is not recorded as a channel.
- **Wake-up and alerts are effects.** `RequestTx` returns them and the caller runs them after the commit (`Engine.Atomic` does both). The wake is built from the catalog's op name, the project, the op hash, the expiry and the pending count: no parameter can reach `notify.Wake`. Critical-class cards raise an alert at request, approval and execution (`Config.Alert`), and their `op.approve` events are `WARN`.

**For the op state machine.** `RequestTx`, `ConsumeTx` and `CancelTx` run inside the caller's `store.DB.Immediate` transaction. `Result.Refusal` and the `*Refusal` returned by `ConsumeTx` carry the denial cause code; on a `Result.Refusal` commit (a stop hook may have written), on a `ConsumeTx` refusal nothing was written. `Config.OnDecided` runs in the decision's transaction (approved, denied, expired) so the op moves in the same commit; call `Engine.Run` (or `Sweep`) on a timer so unanswered cards expire. `approvers.enroll` has a card template and the critical class; issuing the one-time enrolment address after its approval (`console.IssueEnrollment`) and the QR code are done in amendment 9.

### Amendment 9. The phone as built

**Built.** Migration `0007_phone.sql`, `internal/approvals/phone.go`, `internal/console/phone.go` and `phone.html`, `internal/qr`, and `docs/runbooks/phone.md`. Sections 1 to 6 and amendment 6 stand. Decisions made while building:

The server page has "Ask to add a phone": the console, as the operator, requests the critical-class `approvers.enroll` (params `label` and the phone origin) like `secrets.write`. It is approved on the server with Hello. "Show the enrolment address" then spends the approval (`ConsumeTx`) and stores the token hash in one transaction, and answers with `https://<phone host>/enroll#<token>` and its QR code. One approval, one address, 10 minutes, one use. The phone origin refuses to ask for or spend an enrolment, so a stolen unlocked phone cannot add another device. The address is never written to the ledger or a log. The ledger gets `op.request`, `op.approve`, `op.result` for the request, and `chapd`'s existing `approvers.enroll` pair when the credential lands.

Read back with an independent decoder (zxing-cpp, run once by hand during the build, not in CI) for 72 texts across versions 1 to 10; the tests carry a decoder of their own (format bits, Reed-Solomon syndromes, payload) and golden hashes.

## Amendments (2 Nov 2026, console wording)

### Amendment 10. The card is written in plain words, and the plain words are the signed text

**Why.** The Approvals screen was hard to read: a monospace block that began with the operation id, the project, a 64-character hash and the policy version, and only then said what would change. The operator had to find the action in jargon.

**Decision.** The plain wording is the card text itself, not a second text beside it. `renderCard` (`internal/approvals/card.go`) writes card version 2 in this order, and `display_sha256` is still the hash of that exact text, still inside the challenge (section 1):

1. `CHAPERONE APPROVAL CARD v2` (and the CRITICAL banner when the class is critical).
2. `WHAT YOU ARE ASKED TO APPROVE`: `<who> wants to:` then the action in a sentence ("merge pull request #582 into develop"), `Risk:` low, medium, high or critical (for a merge, the pull request's own tier from the `risk_tier` check, else the op's class), what happens on approve and on deny, and when the request runs out. The sentence names everything that decides who receives what: for `mail.send` every recipient class (to, Cc, and the hidden Bcc recipients, counted and listed; a Bcc-only mail reads "send an email to 0 visible recipients and 2 hidden (bcc) recipients") and the attachments; for `drive.share` the recipients, the role and who can see the link (`link_visibility`, or "not stated"). A list element that is not a string is shown as JSON, never dropped. The full values are under WHAT CHANGES.
3. `WHAT CHANGES`: the project, the exact target, the template's fields with plain labels, **and every other parameter** ("Other parameters"). Nothing the decision depends on is ever left for the folded part.
4. `WHY THE REQUESTER ASKS (...; untrusted)`, `CHECKS`, and one `EVIDENCE: <title>` section per piece of adapter evidence.
5. `TECHNICAL DETAILS`: operation id and class, request id, op hash, policy version. Nothing else.
6. `END OF CARD`.

**What the page does, and what it does not.** `approvals.ParseCard` splits the text at those heading lines. A heading is a whole line that untrusted text cannot produce: free text is escaped onto one labelled line, and every line of a block is prefixed `    | `. The split only decides layout: the parts always add up to the card text byte for byte (`ParseCard` refuses a card where they do not, an older version, or sections out of order, and the page then shows the whole text in a `<pre>`). The console lays the parts out (the summary box, the folded technical details, the evidence) inside one element, `.approval-text`, and puts no text of its own inside it. Its `textContent` is the card text, folded parts included; the page script still hashes it and compares it with `display_sha256` before it asks for a challenge, and the challenge still covers that hash. A folded part is on the page and in the hash; folding changes what is visible first, not what is signed. `TestCardTextOnThePageIsTheSignedText` strips the markup of the served page and compares the bytes for several ops, a critical card and a card full of forged headings.

**Derived, not signed.** The one-line list ("Agent r-7f3a (code) wants to merge pull request #582 into develop", the risk word) is read from the same stored card text by `ParseCard` and `CardAsk`, and `Risk` is computed from the same stored approval record that `renderCard` reads. So the line the operator picks from is the text he signs, and a card whose text changes changes the line. What is *not* in the card text, and is drawn from the clock when the page is rendered: the age ("4 min ago"), the time left, the order (soonest to run out first), the colour. The phone's number stays outside the text, as in amendment 9. The fingerprint (`display_sha256`) sits behind a fold on the page and is checked by the script as before.

**Version.** `cardVersion` is now 2. A pending card made by the old template fails the re-render check (`DISPLAY_MISMATCH`) at begin and at phone match, so its text can never be signed: it fails closed. It is **not** asked for again by itself: while it is pending a retry of the same op hash is deduplicated back to it, and when it expires or is denied the op hash is refused for the sticky-deny window (section 6, item 5). So the page shows such a card whole, labelled "an older card: this line is not read from its text", with no Approve button and a plain note; the operator can deny it or let it run out, and the orchestrator asks again after the window. (A requester's cancel starts no window.) This **supersedes the first-line `v1` and the `<pre>` wording of amendment 8 ("What a card shows") and the "same `<pre>`" wording of amendment 9**: the card is one element laid out in sections, as above. The same card element and fragment are used by the server page, the phone page (`web/templates/fragments.html`, `phone.html`) and the Secrets page. No style rule hides any part of the card text (`TestNoStyleRuleHidesTheCardText`).

**Also in this change.** `consumed` is shown as "approved and used", `cancelled` as "withdrawn"; the Home table names the request instead of the op id; the Recent table reads "who wanted to what". The card element has no `tabindex` any more (it no longer scrolls on its own); the evidence section is read in full on the page, as before.

**Not decided here.** Showing what happened after an approved op was released (it can still be refused at release, for example `CI_STALE`): a separate change.

## Amendments (2 Nov 2026, naming the pull request)

### Amendment 11. A merge card quotes the pull request's title, from the adapter's evidence

**Why.** Five pending merges read alike ("merge pull request #582 into main"): the number says nothing to the operator about which change he is approving.

**Decision.** The `pr.merge` adapter adds one evidence block, `EVIDENCE: pull request`, to the card: `Title:` (first line), `Author:` and `Size:` (files and lines), read from the same GitHub request the checks use (`PRVerdict.Subject`). `wantsTo` reads the title from that block and writes `merge pull request #582 "feat(cart): add a delivery fee" into main`.

**The title is the author's text, so the headline escapes all of it (`quoted`, `internal/approvals/card.go`).** Printable ASCII passes, except the backslash and the ASCII quote, which are written `\\` and `\"`. Every other character is written as an escape such as `\u{201D}`: the look-alike quotes (`“ ” ＂ ″ ʺ` and the like), combining marks, bidi controls, zero-width characters and every letter outside ASCII. A title can therefore neither end the quotes nor continue the sentence (`docs: typo” into main; merge pull request #900 “docs: x` reads as one quoted title, and a title that ends in a backslash cannot make the real closing quote look escaped). Because the backslash is escaped too, a typed `\u{202E}` shows as `\\u{202E}` and cannot pass for a real escape. The price is that a title with letters outside ASCII reads in escapes in the headline; the evidence block below it shows the title as written (it goes through `text`, which escapes only what is not printable). The headline is not clipped: it is the text that is merged.

**The evidence keeps the whole title.** `PRSubject.text` writes it without any clip (control characters become `?`). `checkTitle` already limits a title that can be merged to 72 characters and no control character, so for every title that can reach a card the first evidence line is `Title: ` followed by the title, byte for byte. The earlier 80-byte clip and the 80-character clip in `wantsTo` never helped: they cut a non-ASCII title that was allowed (a 72-character title of three-byte characters is 204 bytes) and could not fire on any other. Both are gone. The block's title and the `Title: ` prefix are one pair of constants on each side (`ops.PRSubjectEvidence` and `ops.PRTitlePrefix`, `approvals.EvidencePR` and `approvals.EvidenceTitlePrefix`); the two packages do not import each other, so `cmd/chapd`'s `TestPRSubjectEvidenceWordsAgree` pins them together, and the adapter's own test checks the first line of the evidence it produces. A first line without the prefix quotes no title; it never quotes another line.

**The signed title is the merged title.** The squash commit header is the PR title as read at merge time, so an edit after the operator signed (`pr.update --title` needs no approval) would merge under words he never saw. Two designs were open: (a) a `title` parameter on `pr.merge`, which puts the title in the op hash; (b) compare against the title already stored in the card's evidence. Chosen: **(b)**. The evidence is stored with the card and is covered by `display_sha256`, which the signature covers, and `ConsumeTx` re-renders the card from it and verifies it before it spends the approval. So what the operator signed already includes the title, and (a) would add a second copy to keep equal, put a title lookup in front of every `chap pr merge` (the CLI, its golden files, the API schema and every caller), and change the op hash of every merge. (b) changes no request and no hash. At release, `ops` reads the approval's evidence (`ApprovalInfo.Evidence`, not part of any API view) and hands it to the adapter as `Request.ApprovedEvidence`; `pr.merge` reads the first line of the `pull request` block as `PRMergeRequest.ApprovedTitle`. When it is set:

- step 6 refuses with `title_approved` and `CI_STALE` if the PR's title is another one, so the release check settles the op as refused (an approved op that did not run, with its alert) and no write token is minted;
- step 7, the recheck that reads the PR again just before the write, refuses with `recheck_title` and `CI_STALE`: an edit in the gap between the check and the merge is caught too;
- the merge is sent with the approved title as `commit_title`.

A refusal needs a new request and a new card; it never repeats a title (they are the author's text). The stop stays the spec's `CI_STALE` (the stop table is closed), but `denialtext.NextStep` reads the check name that follows it in the why (`CI_STALE: title_approved:` and `CI_STALE: recheck_title:`) and says to ask again so a new card shows the current title, not to update the branch (which is the step for a real stale branch). A request without an approved title (a low-tier merge that needs no card, or a card made before this evidence existed) is not bound: it merges under the title it reads, checked by `checkTitle`, as before. The code stays pinned by `head_sha` in both cases.

**Signed text and version.** The title is part of the card text and of `display_sha256`, as the whole headline is. `cardVersion` stays 2: the template (headings, order, fixed sentences) is unchanged, and a pending card made before this change has no such evidence, so it re-renders to the very same text and stays signable. The card is always rendered from the stored evidence, so the text that was shown is the text that is re-derived at decision time.

## Amendments (2 Nov 2026, the card inside the dashboard)

### Amendment 12. A separate web front end may show some console pages in a frame

**Why.** The dashboard (an optional, separate web front end for the operator, here at `http://localhost:55440`) is the one place for Chaperone tasks. The operator chose to show the approval card inside the dashboard, not to send them to a second window. Until now every console response said `frame-ancestors 'none'`, `X-Frame-Options: DENY` and refused any request that was not same-origin.

**Decision.** An opt-in, off by default: `chapd -console-frame-ancestor <origin>` (repeatable; plain `http` only for `localhost`; no wildcard, path or userinfo; `console.Config.FrameAncestors`).

1. **An explicit allow-list of pages** (`framablePaths` in `internal/console/guard.go`): `/approvals`, `/ledger`, `/runs`, GET only, and only for a request the browser marks as a frame navigation (`Sec-Fetch-Dest: iframe`). Those responses (and only those) say `frame-ancestors <the listed origins>` and send no `X-Frame-Options` (it has no allow-list form). Every other response, for every other path and request, keeps `frame-ancestors 'none'` and `DENY`. `/secrets` (typing a secret has no second factor, so a page that could overlay a fake field must never be framed), sign-in, enrolment, the phone pages, Home (it holds Stop all) and Operations are not in the list. The test `TestFramingIsAnExplicitAllowList` pins the list and `TestSecretRoutesAreNeverFramable` pins the secret routes.
2. **Fetch metadata** still refuses every same-site and cross-site request, except a GET frame navigation (`Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: iframe`) to a framable page. A GET reads and changes nothing; the session cookie is `SameSite=Strict`, so from a different site the page arrives signed out; and the browser shows the page only inside a listed ancestor. A top-level load of any console page from another page stays refused (403), listed page or not. The operator opens a top-level page by its own address, or from a link inside a frame (a navigation that starts in the console page is same-origin): framed pages carry a link "Secrets: opens in Chaperone" for secret entry, and `/runs` links "Revoke opens in Chaperone". All POSTs, and every other mode or destination, are refused as before. With no ancestor listed nothing is relaxed.
3. **A second WebAuthn verifier** (`relyingParty.waFramed`: `RPAllowCrossOrigin`, `RPTopOrigins` = the ancestor list, explicit mode). `VerifyAssertion` uses it only when the signed `clientDataJSON.crossOrigin` is true, and refuses a cross-origin assertion that names no top origin, or when no ancestor is listed. Sign-in and enrolment never use it: a passkey made in a frame signs nobody in and enrols nobody.
4. **The visibility guard** (`web/static/frame-guard.js`, loaded by every page, active only when `window.top !== window.self`): every control that acts (button, submit input, `hx-post`) is held (`aria-disabled`; not the `disabled` attribute, which Basecoat dims, and IntersectionObserver v2 reports a dimmed element as not visible) until the browser reports it plainly visible (IntersectionObserver v2: fully in view, not covered, not transformed, not transparent); a click on a held control is stopped in the capture phase. A browser without `isVisible` gets no working control in a frame, and the page says so. `?embed=1` only hides the header and the navigation (layout); the guard never reads it.

**What this does not do.** The page that frames us is still a page of another origin: it can show whatever it likes around the frame, and cannot read or script it (different origin, `Cross-Origin-Resource-Policy`, no `postMessage` is read by the console). The signed card is the same text and the same `display_sha256` as before; the passkey prompt and the Windows Hello dialog are the operating system's. Revoke is a session and CSRF action, not a Hello-signed one (it never was), so it is not offered in a frame at all (see the changes after the review below). The iframe needs `allow="publickey-credentials-get"` from the dashboard. Sign-in to the console is not possible in a frame (it is not framable): the operator signs in at the console's own address first, and the frame then arrives with that session.

**Changes after the security review.**
- **The whole card is watched, not only the buttons** (P1). A page that frames us can clip the frame so that only the Approve button shows and draw a fake card beside it; the browser's visibility report for the button alone does not see that. A control inside `article.approval` is armed only while the control and the **signed block** are fully visible (IntersectionObserver v2, ratio 1): the card text (`.approval-text`, every line the hash covers; the technical details and the fingerprint are folded) and the buttons (`.approval-actions`). The card's own summary line and header are not observed (the first version observed the whole `article`, about 1,150 px tall for a deploy card, which a 1080p screen's viewport of 900-950 px can never contain). If that block is taller than the frame, the card says "This card is long: approve it in Chaperone" and links to the console's own window (a same-origin link), where the guard does not apply and the operator approves as before.
- **Timing** (P2). A control is armed only after 800 ms of continuous visibility. A scroll, resize, blur, a hidden tab, a "not visible" report, or a click on a held control disarms everything at once and asks the browser for fresh reports. At click time the queued reports are applied first (`takeRecords`), and the click counts only if the control and its card are visible now and have been for 800 ms.
- **No Revoke in a frame** (P2). `/runs` rendered for a frame navigation has no revoke button for a run or an orchestrator (the server leaves them out; the page cannot be made to show them by a query). The row reads "Revoke opens in Chaperone", a link that opens `/runs` as a top-level window. A Hello-signed Revoke is still not built.
- **No phone panel in a frame** (P3): "Ask to add a phone" and "Show the enrolment address" are not drawn in a frame.
- **The framed verifier is built only for the server's own origin** (P3), not for the phone origin.
- **Links are held too** (final review). The "opens in Chaperone" links (secrets, revoke, a long card) open a signed-in top-level page with no guard, so they are held like buttons: a link arms only after it has been plainly visible for 800 ms (judged on its own visibility, not the card's: the long-card link has to work exactly when the card is not fully in view). The click listeners are registered before the observers are made, the observers are made in a `try`, and `allowed()` answers no when there is no observer, so an exception leaves every control held.
- **Recorded, then narrowed** (re-review). The first version also let any same-site page (any `http://localhost:<port>`) load `/approvals`, `/ledger`, `/runs` and `/secrets` as a top-level document with the session and without the frame guard. That made a "DoubleClickjacking" swap possible (a pop-up replaces its opener with a console page between the two clicks of a double-click). It is gone: only frame navigations are relaxed (item 2). "Cancel and discard the value" on the secrets page also asks for a confirm now.

A changed visibility report (visible or not, how much, where) starts the 800 ms period over. (A first version asked the browser for a new report every 250 ms; the browser run showed each first report is "not visible", so nothing ever armed, and it was removed.)

## Amendments (2 Nov 2026, local time)

### Amendment 13. Times are shown in the operator's local time; the card says both

**Why.** Every time was UTC (`...Z`). For an operator several hours behind UTC, a card that says "expires 2026-11-02T02:18:26Z" looks like tomorrow.

**Decision.**
- **The signed card** (card version **3**) keeps the UTC time and adds the local one on the same line: `Decide before 2026-11-01 22:15 America/Puerto_Rico time (2026-11-02T02:15:00Z). After that the request is dropped.` (the example zone is UTC-4 all year). The zone comes from `internal/localtime`: UTC by default, or the IANA time zone the operator names in `CHAP_TIMEZONE`, read once when the program starts (a name that is not a time zone stops the program). The program embeds the time zone data, so the host needs no time zone database. Both times are in the text that is hashed and signed.
- **Console pages** write each time as `<time datetime="<UTC>">` (the `t` template, or `approvals.js` for the phone address deadline); `web/static/localtime.js` shows it in the configured time zone (default UTC), for example as `2026-11-01 22:15`, and adds the UTC time after it as visible text, in a muted `<span class="utc">(2026-11-02 02:15 UTC)</span>` inside the `<time>`. UTC is not only in a `title`: a title is not reachable by keyboard, touch or most screen readers, and the ledger filters take UTC. Without script the UTC text stays. A `<time>` whose text is not its own datetime (the "4 min ago" in Recent) is left alone. The ledger filters stay UTC and say so.
- **`chap` and `chapd` tables** write the local time as one token with its offset (`2026-11-01T22:15:00-04:00`) under a one-token header that names the offset (for example `EXPIRES(-04)`), so a script that splits on spaces still sees one field per column. `--json` and the API stay UTC.

**Version.** `cardVersion` is 3 because the template text changed. As for version 2 (amendment 10): a pending card made by an older chapd fails the re-render check, so its text can never be signed (it fails closed), and it is not asked for again by itself: the operator lets it run out or denies it, and the orchestrator asks again after the sticky-deny window. A change of the configured time zone changes the card text in the same way. The same holds for an approval granted before the change but not yet used (a merge waiting to run, an "approved, but not stored" secret write): `ConsumeTx` re-renders the card, so it fails `DISPLAY_MISMATCH` and the approval is lost; and the same in reverse after a revert. Install or revert only when no card is pending and no approved card is waiting to be used.

## Amendments (19 Nov 2026, the listener)

### Amendment 14. The real service holds `[::1]` as well as `127.0.0.1`

**Why.** The service bound only `127.0.0.1:55398`, but the operator opens `http://localhost:55398` (section 1: RP ID `localhost`). A browser may resolve `localhost` to `::1` and try it first (Chromium does). Any local program that listens on `[::1]:55398` then receives the console page, the one-time enrolment address, the session cookie and the CSRF cookie, and could relay an approval. The quickstart already closed this for its own port; the real service had not.

**Decision.**

1. `chapd run`, the Windows service (`chapd svc`, which runs the same code) and `chapd enroll` listen on `127.0.0.1:PORT` and on `[::1]:PORT` and serve one handler on both. The shared code is `internal/loopback` (`Bind`); the quickstart uses it too, with its own wording for the IPv4 error. `-addr` supplies the port and must name `127.0.0.1` or `::1` (another `127.x` address is refused); both addresses are always held, so there is no way to hold one side only. The sockets are exclusive on Windows (`SO_EXCLUSIVEADDRUSE`), so another process of the same user cannot share the address.
2. **No IPv6 loopback on the machine**, meaning that taking `[::1]:PORT` fails with "address not available" or "address family not supported" (on Windows `WSAEADDRNOTAVAIL` or `WSAEAFNOSUPPORT`, compared by number): chapd serves on IPv4 only and logs `no IPv6 loopback on this machine: listening on IPv4 only` once, at start. Nothing can be reached through `::1` then. There is no probe on another port: a probe can be made to fail by a program that uses up the ephemeral ports, and any failure other than those two is treated as item 3.
3. **Anything else goes wrong taking `[::1]:PORT`** (address in use, no buffer space, too many open files, access denied): chapd does not start. The port is taken before `Start` (crash recovery, sweeps, release of approved ops), so a service that restarts does not repeat that work each time, and the Windows service reports Running only after it holds the port. The listeners are open while `Start` runs: the system completes connections into the backlog and clients wait, but nothing is read or answered until `Start` has finished and `Serve` begins. The error names the address and says another program is there and why that matters; the IPv4 listener is given back first. The Windows service exits with a service-specific failure, so the recovery action retries about every 30 seconds without end, and the message is in `chapd.log` when the service was registered with `-log-dir` (the installer does that). This fails closed on purpose: starting anyway would leave the squatter in the browser's path.
4. **The API on both addresses, one handler.** `chap` uses `CHAP_URL` on `127.0.0.1` and is not affected. The alternative (console on both, API on IPv4 only) needs a second handler and a second listener set for no gain: an API call needs a bearer token, and a client would reach the IPv6 side of the API port only by naming it, which the Host check refuses. One handler keeps the Host and Origin checks identical on both stacks (tested: the same answers on both addresses for every Host). It also means nothing else can listen on the API port's IPv6 side.
5. **The Host and Origin checks did not change.** The console accepts Host `localhost:PORT` only; the API accepts `127.0.0.1:PORT` and `localhost:PORT`; Host `[::1]:PORT` is refused by both (`403` console, `421` API), as before. A browser at `localhost` that reaches the server over `::1` still sends Host `localhost:PORT`, so the passkey origin is the same.
6. Amendment 6, item 2 stands: `tailscale serve` proxies to `http://127.0.0.1:55398`; chapd now also holds `[::1]:55398`, which Tailscale does not use.
7. **Known operational risk, not proven and not bounded in code:** the Windows service now stays in the start-pending state until it holds the port, and in that state it accepts no stop control. If `Build` or `Listen` blocked (a database that cannot be opened, say), the service would sit there instead of being Running and stoppable; the service manager's own start timeout is the bound, and the recovery action then applies. I did not add a timeout around `Build`: a start that is slow for a good reason (a large migration) would be failed and restarted in a loop, and the service loop cannot be tested without the service manager. If it happens, kill the `chapd.exe` process; the log (`-log-dir`) shows where it stopped.

**What this does not protect against.** A program that listened on `[::1]:PORT` before chapd started is detected only when chapd starts. One that takes the port after a chapd crash, before the restart, still gets what the browser sends there (it still cannot make a valid assertion: the passkey is bound to the origin and the card hash). It does not stop a program that binds the port on another address of the machine (nothing sends `localhost` there), or an administrator. `chap doctor` still checks only the IPv4 side and the other interfaces; it does not check `[::1]` (open item for the doctor's owner). If IPv6 is turned on after chapd started on IPv4 only, `[::1]:PORT` stays free until chapd restarts. Cookies are not scoped to a port: any web server the operator opens at `localhost:<other port>` receives `chap_session` and `chap_csrf`; that is enough for session-level actions (look, deny, revoke) but not to approve, which needs a fresh passkey assertion. This was so before this amendment.

## Amendments (19 Nov 2026, authenticators that are not built in)

### Amendment 15. A hardware security key or a phone passkey may approve, if the operator opts in

**Why platform authenticators were chosen, and what that cost.** Section 1 and the Context say what the approve proves: a user-verified WebAuthn assertion means the person at the machine unlocked a key (PIN, fingerprint or face), and a script running as the same user cannot produce that. Windows Hello was the authenticator the first version was built and tested against, so registration asked for `authenticatorAttachment: platform` and refused a credential the browser reported as anything else. A Linux desktop usually has no built-in authenticator, and a Mac or Windows PC with no PIN or biometric set up has none usable. Those operators had no way to approve at all. The property that matters (user verification) does not depend on the authenticator being built in. The attachment rule was a convenient way to get a known authenticator, not the control.

**Decision.** One install-level setting, `Authenticators` (`chapd run -approver-authenticators platform|any`, and the same flag on `chapd enroll`):

| Setting | Registration asks the browser for | Accepted | Who it is for |
| --- | --- | --- | --- |
| `platform` (the default) | `authenticatorAttachment: platform` | Reported `platform`, or not reported | Every install that exists today, and anyone with Windows Hello or Touch ID |
| `any` | no attachment (the browser offers the built-in authenticator, a phone through its cross-device ("hybrid") prompt, and a USB, NFC or Bluetooth security key) | `platform`, `cross-platform`, or not reported | A Linux desktop, or anyone who prefers a security key |

**Kept for every setting and every kind, unchanged:** user verification required at registration and at every sign-in and every approval (the UV flag is refused when clear, checked by us as well as by the library, for a security key exactly as for Windows Hello); user presence; a discoverable credential (`residentKey: required`); attestation `none`; the Host, `Origin` and RP-ID checks; the per-credential `rp_id` and `origin`; the sign-count rule (a counter that goes backwards is refused, a counter that stays 0 is fine) and the library's backup-eligible and backup-state consistency checks; single-use ceremonies; the challenge over the card hash; and **the first approver is enrolled only with the one-time address at the local origin** (`chapd enroll` or the quickstart). A security key does not change who may enrol: no address, no credential. Tests: a security key with UV is accepted under `any` and refused under `platform` (and the refusal does not spend the one-time address); UV off or UP off is refused under both settings, at registration, at sign-in and at approval; the platform flow is the same under both.

**The setting is per install and is not silently widened.** Options considered: (a) a field in the policy pack (`baseline.yaml` and `policy/<project>.yaml`); (b) a flag, like `-phone-host`; (c) a per-credential choice by the operator at enrolment. Chosen: (b). The baseline pack is compiled in and a project file can only narrow it, so "allow more" does not fit there; this is a per-machine trust decision, the same kind as `-phone-host` and `-console-frame-ancestor`, and a flag is visible in the service's command line. Option (c) would let whoever holds the one-time address pick the weaker kind. The default stays `platform` for every existing install: a binary upgrade changes nothing until the flag is added. Starting with `any` writes one warning to the log.

**Recommendation for new installs** (not built; for the owner to decide): keep `platform` as the default of the binary (the shipped, tested path), and have the install script ask "Does this machine have Windows Hello or Touch ID?" and add `-approver-authenticators any` only when the answer is no, or the operator wants a key. The quickstart playground uses `any` for itself, because it guards a fake GitHub and its folder is a new install.

**Narrowing.** Removing the flag (or setting `platform`) refuses every credential whose recorded attachment is `cross-platform`, at sign-in and at approval (`attachment_not_allowed`), so a key enrolled while it said `any` cannot be used after the operator narrows the setting again. Under `any`, a registration whose browser did not say what kind it was (or said something the library drops) is recorded as `cross-platform`, the wider kind, so it is stopped too; under `platform` it stays unrecorded and is accepted, as before. Console sessions made with a refused credential end at once (the session lookup checks the credential), and chapd logs at start how many enrolled credentials the setting refuses. **A lockout to avoid:** narrowing while the only approver has a security key or phone passkey leaves nobody able to sign in, and `chapd enroll` refuses because an approver exists. **There is no way today to add a passkey at `localhost` to an existing approver**: `chapd enroll` refuses once an approver exists, and the `approvers.enroll` flow of the phone page (`phone.go`, only when phone access is configured) enrols a passkey at the phone origin only. So an operator whose only passkey at the PC is a security key or a phone passkey made at `localhost` must stay on `any`; narrowing is safe only where a passkey that `platform` allows already exists for the approver at `localhost` (made under `platform`, or by Windows Hello under `any` with a browser that reports `platform`). The way out of a lockout is the flag again. At start chapd logs the count of refused passkeys: a warning when some still work, an error with that instruction when none does. It still starts in the second case: refusing to start would turn a setting mistake into an outage for agents doing routine work that needs no approval. `chapd enroll` and `chapd run` must be given the same value.

**Synced passkey or device-bound.** A passkey made on a phone is normally backup-eligible (BE=1): iCloud Keychain, Google Password Manager or a password manager keeps a copy that a new device can restore. A hardware security key, and a Windows Hello key held in the TPM, are device-bound (BE=0) `[INFERENCE: not measured here]`. The console already stored `backup_eligible` and `backup_state` per credential (amendment 6); BE now also goes into every event and ledger line. A synced passkey is as strong as the account that syncs it: whoever takes over the Apple, Google or password-manager account (and passes that provider's own check on a new device) can approve. A device-bound one needs the device. Nothing refuses BE=1 now: that would lock out phones, and the choice belongs with the operator. Forbidding it later is one more value of the same flag (for example `any-device-bound`); it is not built.

**A phone passkey over the cross-device flow at `localhost`** works as an authenticator only: the browser on the server shows a QR code, the phone makes or signs with its passkey (its screen lock is the user verification), and the assertion is for RP ID `localhost`. The card stays on the server's screen, the channel is `pc`, and there is no number matching. It is not the independent second display that the phone page of section 5 gives (there the phone shows the server-rendered card at its own origin). Use the phone page when a second display matters; use the cross-device flow when only an authenticator is missing.

**What is recorded about the authenticator.**

- Every credential row stores `attachment`, `transports`, `backup_eligible`, `backup_state` and `aaguid` (already so). With attestation `none` the AAGUID is usually zero, so the model of the key is not known: the attachment and transports are what the browser says.
- `console.enrolled` and `console.login` events carry `Attachment`, `Transports` and `BackupEligible`, and `chapd enroll` prints them on its `OK` lines. The first enrolment's `approvers.enroll` ledger body and every `console.login` body end with `authenticator=<platform|cross-platform|unreported>; transports=<list|none>; backup_eligible=<true|false>`. The transports are filtered to `usb`, `nfc`, `ble`, `smart-card`, `hybrid` and `internal`, once each, before they are stored, and again whenever an event is built, because the browser sends them as free text and the library accepts any string: a forged value cannot add fields to a ledger line or put text on the terminal of `chapd enroll`. The spec closes the attributes of `console.login`, so this travels in the body.
- Every `op.approve` body of an approval carries the same three facts, taken from the credential that signed. An auditor reads which kind approved from the ledger line, and can reach the credential row from the credential id in `approval_assertions`.
- **The signed card text and `display_sha256` do not change.** The kind of authenticator is not known when the card is rendered and hashed, and the card text is covered by tests and hashes (amendment 10). The spec's `confirmations[]` object is closed (`channel`, `credential_id`, `assertion_sha256`, `at`), so it gains nothing here; a field for the authenticator kind is a proposal for the spec's authors.
- A refusal for the attachment is `console.refused` with reason `attachment_not_allowed`. Before this amendment the same case was `credential_not_allowed`; only the code differs.

**Console wording.** The sign-in, enrolment and approval pages and the `chapd enroll` text no longer name Windows Hello or Microsoft Edge: "Sign in with a passkey", "Approve with your passkey", "Create passkey". The pages explain the choices (built in, security key, phone) only when the setting is `any`. The Windows demo script `scripts/demo/approve-a-merge.ps1` is Windows-specific and still names Windows Hello and Edge.

**What this does not protect against.**

- **A roaming key left plugged in** still needs its PIN or fingerprint for every assertion (UV is required and refused when clear): plugging it in is not approval `[INFERENCE: browsers ask for the PIN again for each assertion; not checked on hardware]`. A key with a weak, shared or default PIN, or a PIN an attacker can watch being typed, is only as good as that PIN. An authenticator that lies about UV (a software authenticator, or a key that claims UV without a PIN) cannot be told apart: attestation is `none`. The same was true of Windows Hello, so no property was lost, but the set of authenticators the operator has to trust has grown.
- **Malware on the same user account** that drives the browser can still ask the operator for an approval at a moment he is expecting one. The protection is the card the operator reads (amendment 10), not the kind of key.
- **The attachment is what the browser says, not proof.** A script that posts to the console directly can claim `platform`. It still needs the one-time address (first approver), a fresh user-verified signature from a key the console enrolled, and the challenge over the card hash. The setting is a policy about which kinds the operator meant to allow, not a barrier against a local attacker who already has those.
- **A synced passkey** is exposed to account takeover at the provider (above). A phone used through the cross-device flow also depends on the Bluetooth proximity check done by the browser and the phone, not by Chaperone.
- **The one-time address** still goes to whoever opens it first; amendment 14 closes the `[::1]` route to it, nothing here changes the rest.

**To verify with real hardware (needs a person).** (1) A FIDO2 security key with a PIN, on a Linux desktop with Chrome or Firefox: enrol with `chapd enroll -approver-authenticators any` (or the quickstart), sign in, approve a card; the ledger line must say `authenticator=cross-platform; transports=usb`. (2) A phone through the "use a phone" prompt: the browser must report `cross-platform` with `hybrid`, and the line must say so. (3) The same key under the default setting: registration is refused with `attachment_not_allowed`. (4) A key with no PIN set: the browser must ask to set one, and enrolment must not succeed without user verification. (5) Windows Hello on the server still enrols and approves under both settings.
