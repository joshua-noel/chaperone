# ADR-008: Custom keys: a Chaperone token for a script or an agent

- **Status:** **Accepted** (operator decisions of 3 Nov 2026, as written in the rules below). Written 2026-11-20 from the code that implements them: `internal/keys`, `internal/ops/keyceiling.go`, migration `0010_custom_keys.sql`.
- **Decides:** how a script or an agent gets its own credential for a small part of what Chaperone can do, without the orchestrator's token and without any vendor secret; what that credential can never do; how it is made, shown, limited, ended and written down.
- **Does not decide:** which ops a key may hold beyond the first ones (the list grows in `internal/ops/keyceiling.go`, one reviewed change per op), or how a stopped agent is resumed (not built).

## Context

- Until now Chaperone knew two callers: a run (ADR-005) and the orchestrator (ADR-007). A script or an agent that is not a run had to borrow the orchestrator's token, which holds every op the orchestrator holds.
- A key is **not** a vendor secret. It never holds a GitHub or Linear credential. It names what Chaperone will do, and every call under it goes through the same policy, approval card, rate limit and ledger as any other call.

## Decision

**A key is an opaque bearer token, made in two steps, stored only as its SHA-256, bound to one project, a list of ops and the repositories it covers, with an expiry and an hourly rate that are fixed when it is made.**

1. **Format and storage.** `chap_key_` followed by the base64url of 32 random bytes. The `chap_key_` prefix routes the bearer to the key verifier. The database keeps only `SHA-256(token)` and the first 8 hex characters as a fingerprint. Verification reads the row on every request, so a revoked key stops at the next call.
2. **Making a key takes an approval.** The op `keys.issue` is class **high**: a card the operator signs with Windows Hello or a phone passkey. The card lists the holder, every op (sorted), the repositories, the lifetime and the rate, in the words and the order the key will hold them: the adapter refuses a request whose lists are not already sorted, lower-case and free of repeats, and a request that leaves out the lifetime or the rate. Only the orchestrator's token may ask for it, and a key asked for directly may hold only ops that the orchestrator's own token holds (its `scope.ops`, patterns included): a key never reaches past its owner. The orchestrator's ops are stored with the op, so the check holds when the approved op is released too. It ships off in the baseline.
3. **The claim.** The signed card writes the key's row with **no token**. The caller that asked then claims it, once, within one hour: the token is made at that moment, only its hash is stored, and it is registered with the redaction registry before the row commits. The one claim response carries it (`Cache-Control: no-store`); nothing else, not an op result, a ledger event, a log line or an error, ever does. A key not claimed within the hour is revoked by a sweeper.
4. **What a key may hold (rule R1).** A key runs routine ops on its own. For a risky (non-routine) op it can only **ask**: every use raises its own approval card, the operator approves each one with a passkey, and nothing runs until then. The owner decided on 20 Nov 2026 to keep this: a key may hold a risky op ask-only. A key that holds one is *sensitive* (at most 7 days). A key can never hold a critical op, never `keys.*`, `people.*`, `roles.*`, `secrets.*`, `issue.*`, `intake.*`, `ci.report`, `policy.activate`, `approvers.enroll`, `repo.settings` or `host.scripts.refresh`. Only an op that names the unit it is bound to (a repository or the project) can be in a key, so no key means "everything". The ceiling is checked three times: when the card is made, when the key is verified (a row that lists a critical or never-in-key op does not give the key that op: the list is cut down to what a key may hold, the sensitivity is worked out again from the ops, and a life longer than 7 days for a sensitive key, or than 30 for any key, is refused) and when each op is asked for.
5. **Scope is fixed.** Project, ops, repositories, rate and expiry never change after issue (database triggers refuse an update). A key cannot name another project in a request. A pull-request read under a key is refused before any call to GitHub unless the repository is one the key covers. The triggers and `CHECK`s guard against a bug and an update. They do not stop someone who can write the database, who is the trusted administrator: such a person could drop a trigger, or insert a row for another project or other repositories. What is proved is narrower, and is said in item 4: a row cannot give a key a critical or never-in-key op, or a life longer than the limits.
6. **Limits.** At most 30 days; a sensitive key at most 7. At least 1 hour. At most 300 calls an hour over all ops, lowered only. The database repeats the lifetime limits in `CHECK`s.
7. **What a key can never do.** Decide an approval card (a key that tries is a `POLICY_BREACH`), issue or revoke another key (it may revoke itself), use the git proxy, or read the ledger.
8. **Revoking.** An orchestrator lists, reads and revokes only the keys it **owns** (it asked for them) in the projects its own token covers, and reads only the requests of agents it owns: another owner's key or request looks like no key. It never holds `keys.*` operations for this: the routes need only the token. A key revokes only itself. A revoke by a token is **never a human stop**. A key owned by a person is revoked at the console only: **Agents → Revoke**. That needs the signed-in session (with its CSRF token, same-origin and never-framed rules, like every console action) and no passkey tap: revoking only takes access away, and the console already revokes a run, an orchestrator and a waiting card, and denies a request, on a session alone. That console revoke is the human stop: it also stops an **agent**, so no key can be issued for it until its owner resumes it ("stopped by a human: ask your owner"). The revoke, the cancel of the key's pending approvals and waiting ops, and its ledger events are one transaction. One live key per agent: a new grant replaces the earlier one. **A key does not outlive the access of the orchestrator that built it.** Only its owner could read or revoke it, so when the operator revokes an orchestrator every key it owns is revoked in the same transaction, and when its token is re-issued without a project, or without an operation a key it owns holds, those keys are revoked in the re-issue transaction (a key is judged against the new scope alone: its project must be in it and each of its ops allowed by it, so a re-issue that keeps both leaves it). Both are chapd's own, never a human stop, and one `keys.revoke` event each, by the ledger id `chapd` (reserved: no orchestrator may carry it). Revoking on the re-issue was chosen over refusing the re-issue until the keys were revoked by hand: it is simpler and safe, since the operator has just narrowed what the orchestrator may touch. **The operator can always see and end a key at the console**: **Agents** lists the keys of the operator's own agents and every key an orchestrator owns, with the owner shown, each with Revoke. Revoking an orchestrator's key there is not a human stop (the orchestrator may ask again; each ask is a card). Another person's agent still looks like no agent, since people are not modelled.
9. **A key runs only while it lives.** A key is read once, when its token arrives. The release of an approved op asks the key store again, inside the transaction that releases the op and spends its approval (`ops.Config.KeyLive`, `keys.Store.Live`), and a revoke cannot interleave with that transaction. So a call that was in flight when the key was revoked, and an op whose card was signed after the key had expired, are refused (`TOKEN_REVOKED`, `TOKEN_EXPIRED`) and the approval is not spent. A run token and an orchestrator token are read once the same way, and the release of their ops does not ask again, so the same few-microsecond window exists for them (read from `internal/ops/auth.go` and `lifecycle.go`; not shown by a test). This ADR does not change them.
10. **The ledger.** The spec has no key requester, so a key is written in the ledger as the orchestrator `key.<id>` (the one projection is `internal/spec/keyrequester.go`), and the event body names the key, its owner and its holder. The approvals and ops tables keep a separate requester kind `key`.

## What this does and does not defend

| Attacker | Result |
| --- | --- |
| A script that holds a key tries an op outside its list, another repository or another project | Refused with a denial; nothing reaches GitHub |
| A key tries a critical op, `keys.issue` or a card decision | Refused; a card decision is a `POLICY_BREACH` |
| Someone who reads the database | Finds hashes, never a token |
| A stolen key | Works until its expiry or a revoke, inside its scope and rate; a risky op still needs a card |
| A request that tries to widen a key after the card was signed | The card is made from the request: what is signed is what is stored; the row's scope never changes |
| An orchestrator token (even one that holds no `keys.*` op) tries to list, read or revoke the keys and requests of someone else's agents | Sees nothing of them; its revoke is refused as "no such key", and the agent is not stopped |
| An orchestrator asks for a key with an op its own token does not hold | Refused before a card is made: a key never reaches past its owner |
| A call is in flight when its key is revoked, or an approved op outlives its key | Refused at release; the approval is not spent |
| Another user on the machine reads the key file | The file is private to the user from the moment it exists: mode 0600, or on Windows a protected access list for the user alone |

## Open

- Resuming a stopped agent has no command yet.
- Owners are the orchestrator that asked: there is no model of people yet.
- The ceiling holds the four pull-request reads, `health`, `logs` and `deploy` (ask-only).

## Amendments

**Amendment 1. The agent asks, you tap (2026-11-20).** An agent no longer needs the orchestrator to ask for a key for it. The code is `internal/keys` (`enrol.go`, `requests.go`, `decide.go`, `extend.go`, `scope.go`, `access.go`), migration `0011_agent_requests.sql`, the console's **Agents** pages and `chap agent enrol`, `chap key request`, `chap key extend`. The operator steps are in [`../runbooks/custom-keys.md`](../runbooks/custom-keys.md).

- **Enrolment, once.** The agent starts a device-code flow (the shape of RFC 8628): it gets a short code to read out and a long one only it holds. Neither is stored, only their SHA-256. The owner types the short code at the console, reads "no access at all" and signs a `keys.issue` card with their own Windows Hello. The agent's next poll hands it a **request-only key** once: 30 days, no op, 60 calls an hour. The only thing it can do is ask.
- **Asking.** `keys.request` is routine. It writes the ask down and raises no card. An agent's key holds it without listing it, and no other key does. Identical asks are one request. The owner's reading of the reason is of the agent's own words, shown as text, cleaned with the shared cleaner of the connectors (`untrusted.Line`): control, bidirectional and zero-width characters become spaces. An agent label is at most 40 characters, so the ledger id derived from it (`agent.<owner>.<label>`) always fits the ledger's 63; a longer label is refused when the enrolment starts. Caps keep a looping agent from filling its owner's queue: at most 3 requests wait per agent, 6 new per hour per agent, 10 per owner, 20 in all; a denied exact ask is refused for an hour. `--same-as-me-read` is expanded by chapd to the read ops the owner may grant.
- **Answering.** Grant as asked, narrow and grant, or deny. A grant can only remove ops or repositories, shorten the lifetime or lower the rate; the same check runs when the card is made and again when the key is written. Grant and narrow only make a `keys.issue` card, started by chapd as the caller `operator` (an orchestrator id that no token can carry: `chapd orch issue` refuses it). The key exists only when the owner signs that card with their own Hello. Another person's signature does not make it, and another person's agent looks like no agent.
- **Claiming.** The agent claims the granted key; the claim writes it over the request-only key, which is revoked in the same step. One live key per agent.
- **Extending.** `keys.extend` changes the expiry and nothing else, never past 30 days from the day the key was made (7 with a risky op), and only for a live key an owner granted their own agent. The owner taps **Extend 24 hours**, or the agent asks; either way it is a card the owner signs.
- **The routes that need no credential.** `POST /v0/agents/enrolments` and its poll are the only two routes of chapd that take no token, because the agent has none yet. Their bounds, all tested (`cmd/chapd/agent_enrol_bounds_test.go`): at most 5 enrolments wait, even under concurrent starts; one label waits once; an enrolment lives 10 minutes; a wrong code is counted per owner, five in ten minutes lock that owner's code box (also against the right code), and starting new enrolments does not reset the count; the routes answer only on chapd's loopback listeners, only for the Host the rest of the API answers to, and refuse any request with an `Origin` header or without a JSON content type, so a web page in the operator's browser cannot use them. A wrong device code, an unknown id and a malformed id get the same answer.
- **What a local process can still do.** With no credential, a process on the machine can hold the 5 slots, or the one label of the agent it wants to block, for 10 minutes at a time, and repeat. The real agent is then refused with 429 or 409 until the enrolment expires. Nothing can stop this (a limit per source cannot work on loopback), so it is made visible: a refused start is written once a minute for each label to the log (a WARN) and to the ledger (`keys.enrol`, outcome refused, cause `ENROLMENT_REFUSED`), and the **Agents** page lists every waiting enrolment with its label, project and age, and a Cancel button (a session is enough: cancelling only takes away; any signed-in approver may cancel any waiting enrolment, because until an owner answers it has none, as any approver may deny a card; the ledger names the approver, `keys.enrol.cancel`). The note is limited per label (and ten a minute in all, with a clash on a label that holds a slot outside that cap), so neither a squatter's refusals nor a flood of other labels hides the real agent's. The attacker cannot turn this into a key, because the owner types a code that only the real agent printed.
- **The wrong-code count is in memory.** A restart of chapd clears it.
- **Who owns an agent.** Until people are modelled, the owner is the console approver who enrolled the agent (`person:<approver id>`), and every approver's access is everything the policy allows.
