# ADR-002: GitHub identity, and how `pr.merge` enforces "verify on the exact head"

- **Status:** **Accepted** (operator sign-off). Amended 2026-10-24 (amendments 1 to 4: no agent holds a GitHub credential, the agent account split, risk-tiered review, and the orchestrator as a caller): see "Amendments" at the end. Decision item 3 ("Identity in GitHub's audit trail") and step 5 of the `pr.merge` algorithm carry the amended text. Amended 2026-10-26 (amendment 8, amendment 9): the git proxy keeps one token per run, repository and permission set until the run ends, and repeats a 404. Amended 2026-10-31 (amendment 10): step 3 may, per project policy, also or instead read a local CI result that Chaperone's own App posts through `ci.report`; nothing else changes it.
- **Decides:** which GitHub credential Chaperone uses, how agents get GitHub access without holding a credential, and the exact `pr.merge` algorithm.
- **Inputs:** the maintainers' decisions to stay on the GitHub Free plan and defer Team ("Until then, Chaperone's `pr.merge` is the enforcement"); the merge procedure of an example project (the procedure this ADR turns into code); an incident on 2026-10-18 when a pull request was merged on stale CI; factory-spec v0 `run-token.schema.json` (`task_scope.repo/base/branch/ops`).

## Context: what GitHub can and cannot do for us on Free

- **Branch protection and rulesets do not apply to our private repos on Free.** GitHub's docs: protected branches are available in public repositories with Free and Free for organizations, and in public and private repositories with Pro, Team, Enterprise Cloud (<https://docs.github.com/en/rest/branches/branch-protection>); rulesets are "for customers on GitHub Team and GitHub Enterprise plans" (<https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets>). The example project's repository confirms it: the protection API answers 403 "Upgrade to GitHub Pro" (see the incident above). So nothing on GitHub's side stops a push to `main` or a merge of a red PR. **Chaperone is the only control**, and it must be the only holder of a credential that can do either.
- **An installation token cannot be scoped to a branch.** The create-token endpoint takes `repositories` / `repository_ids` (up to 500) and a `permissions` object, and nothing else (<https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app>). The original design's line "a token scoped to `agent/*` branches" is not available from GitHub. Branch scoping has to be done by Chaperone on the wire (see "Push path").
- **Token lifetime and format.** Installation tokens expire after one hour. Since the staged rollout that began 2026-04-27 and finished 2026-10-02, new tokens are stateless `ghs_APPID_JWT` strings of about 520 characters (the old ones were 40); GitHub says treat them as opaque and do not validate them client-side (<https://github.blog/changelog/2026-10-02-stateless-github-app-installation-tokens-rolled-out>, <https://github.blog/changelog/2026-04-24-notice-about-upcoming-new-format-for-github-app-installation-tokens>). The temporary format-override header ends 2026-11-30; do not send it.
- **Revocation.** `DELETE /installation/token` is still documented: it "invalidates" the token used to call it (<https://docs.github.com/en/rest/apps/installations#revoke-an-installation-access-token>). The docs do not say how a *stateless* token is revoked. `[INFERENCE]` it works as documented; **an acceptance test proves that a revoked token gets 401**, so we find out before we rely on it.
- **A workflow-file push needs a permission of its own.** The App permission `workflows` (value `write` only) is "update GitHub Actions workflow files" (same REST page). An installation token minted **without** it cannot push changes under `.github/workflows/`, so "workflow-file edits need approval" (a rule of the original design) is enforced by GitHub itself when the token lacks the permission. `[INFERENCE: standard GitHub behaviour; a test against a scratch repo covers it]`.
- **Fine-grained PATs** (<https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens>, <https://docs.github.com/en/organizations/managing-programmatic-access-to-your-organization/setting-a-personal-access-token-policy-for-your-organization>): limited to one resource owner each; org owners can require approval before an org-scoped token works (it stays `pending`, public-read only, until reviewed); the org's default maximum lifetime is 366 days; "infinite lifetimes are allowed but may be blocked" by org policy. A PAT acts as the person who made it.

## Decision

**A GitHub App owned by `example-org` (name `chaperone-app`), installed on each project repo. `chapd` holds the App private key in the vault (ADR-003) and mints installation tokens itself. Agents never receive a GitHub credential of any kind.**

1. **Minting.** `chapd` signs a short App JWT with the key, then calls the create-token endpoint with `repositories: [<one repo>]` and the **minimum permissions for that one operation**:

   | Use | Permissions | Where the token lives |
   | --- | --- | --- |
   | Evaluate a merge (read PR, check runs, compare) | `pull_requests: read`, `checks: read`, `contents: read`, `metadata: read` | memory of `chapd`, one operation |
   | Fetch / clone for a run | `contents: read` | memory, until the run ends |
   | Push `agent/*` branch | `contents: write`, `pull_requests: write`, `metadata: read` (**no `workflows`**) | memory, until the run ends |
   | Open PR (`pr.open`) | `pull_requests: write`, `contents: read`, `metadata: read`. GitHub validates head and base with the token; without `contents: read` it answers 422 `not all refs are readable` (found live, 25 Oct) | memory, one call, then revoked |
   | Merge | `contents: write`, `pull_requests: write`, `metadata: read` | memory, **only for the single merge call**, then revoked |
   | Push touching workflow files | adds `workflows: write` | **Disabled in Phase 1**: the App is not granted `workflows` at all, so the op `pr.push.workflow` stays off and workflow edits are pushed by the operator by hand. If it is enabled later: tier `approve`, single push, token revoked after |
   | Record a deploy (replaces `record-deploy.mjs`'s use of the operator's `gh`) | `deployments: write` | one call |
   | Post a local CI result (`ci.report`, amendment 10) | `checks: write`, `metadata: read` | one call, then revoked |

   "Per run" in the question: the token is **minted per run and per operation, held by `chapd`, revoked when the run ends** (ADR-005). The agent holds a run token only; it never learns a `ghs_` value.
2. **Push path (this is how `agent/*` is enforced).** `chapd` serves a git smart-HTTP reverse proxy. The agent's remote is `http://127.0.0.1:55398/git/<owner>/<repo>.git` (set by `chap git setup`; the egress proxy routes it in Phase 2). For `git-receive-pack`, the proxy reads only the **update-request**: the pkt-line command list that ends at the first flush-pkt, before the pack data (`create`/`update`/`delete` = `old-id SP new-id SP refname`, per <https://git-scm.com/docs/pack-protocol>). It forwards the request with the injected token only if **every** command's refname equals the run token's `task_scope.branch` (the schema allows exactly one concrete branch) and the command is not a delete of anything else. A `push-cert` block, tag refs, `refs/heads/<base>`, or any other ref are refused with `SCOPE_BRANCH` and a structured denial. The remainder of the body is streamed, not buffered. Request bodies may be compressed or chunked; the proxy must decode before parsing `[INFERENCE: standard git HTTP transport behaviour; a test proves it with real `git push` of large and small pushes]`. Fetch (`git-upload-pack`) is allowed for the run's repos only.
3. **Identity in GitHub's audit trail.** Pushes carry the agent's git author as before. PRs opened with `pr.open` and merges are performed by the App's bot identity, not the operator. The operator's own `gh` login stays on the server for human use, in the operator's profile only. **Chaperone pushes and merges; no agent holds a GitHub write credential of any kind** (no `GH_TOKEN`, no `gh` login, no deploy key, no PAT in its profile or environment). The orchestrator (the lead agent that coordinates other agents) reaches GitHub for these ops through `chap` with its orchestrator token (ADR-007), not with a credential of its own. The cut-over removes `GH_TOKEN` and similar from the agents' environment and proves it with `env`, `gh auth status` and `git config` output in the PR. The account split (amendment 2) makes this checkable: agents run under their own Windows account, whose profile has no `gh` config to find.
4. **Which repos.** The App is installed on `example-org/storefront` first, then on `chaperone`, `runner` and `factory-spec`. The runner is a separate project that starts agent runs and signs their run tokens; it is not yet public. `chapd` refuses a repo that is not in the project manifest even if the installation could reach it.

## `pr.merge`: the algorithm

Input: `repo`, `pr` number, optional `expected_head` (if the caller gives one, it must equal the head found in step 2). One merge per repo at a time (a per-repo mutex in `chapd`, mirroring "one merge at a time" in the example project's merge procedure). **Never loop on a refusal** (house rule): the result is returned to the caller.

1. **Authorize.** Run token verified (ADR-005); `pr.merge` is in `task_scope.ops`; `repo` equals `task_scope.repo`; the project policy enables the op for the caller's profile. Else `OP_NOT_IN_TOKEN` / `OP_DISABLED`.
2. **Read the PR** (read token): `GET /repos/{o}/{r}/pulls/{n}`. Require `state=open`, `draft=false`, `base.ref` equals the project's merge base (e.g. `develop`), `head.repo.full_name == repo` (no forks), `mergeable != false`. Record **`H = head.sha`**. If the caller supplied `expected_head` and it differs, refuse.
3. **Find the verify result for exactly H.** `GET /repos/{o}/{r}/commits/{H}/check-runs?check_name=verify&app_id=15368&filter=latest` (the check-runs endpoint takes `check_name`, `filter` and `app_id`; <https://docs.github.com/rest/checks/runs>). **`app_id=15368` is GitHub Actions** (I confirmed `https://api.github.com/apps/github-actions` returns `id: 15368`). Filtering by app stops a commit status or another App from posting a fake `verify`. Require exactly one result with `status=completed`, `conclusion=success`, `head_sha == H`. `in_progress`, `queued`, `cancelled`, `skipped`, `neutral`, `failure`, a missing check, or more than one are all **refuse** (this is the written rule in the merge procedure: "treat missing, `in_progress`, `cancelled` or `skipped` as not yet"). Project policy may add more required check names. Cause codes: `CI_RED` / `CI_STALE` from the stop table, reported through the denial `OP_POLICY_REFUSED` with the failing `checks[]` names.
4. **Base is current.** `GET /repos/{o}/{r}/compare/{base}...{H}`; require `behind_by == 0` (the field exists in the compare response; <https://docs.github.com/en/rest/commits/commits#compare-two-commits>). If not, refuse with a hint to run `pr.update` (below). This is "`mergeStateStatus` of `BEHIND` means go back to step 2" from the procedure.
5. **Risk tier and workflow files (risk-tiered review).** `GET /pulls/{n}/files`; classify the PR by **path, not by author**. Tiers and globs are policy data (`policy/<project>.yaml`, narrowing only); the baseline is: **low** = docs, tests and anything flagged low (merges on the checks above, no human step); **medium** = any other code path (needs one human approval card, the "one tap"); **high** = `.github/workflows/**`, migrations, host scripts, auth and payment code, deploy files (needs an approval card that shows the diff). Medium and high require an **approval bound to the op hash** (it includes `H`), tier `approve` (ADR-004; one device is enough for every approval class). A bot's or an agent's approval never satisfies the human slot. No approval pending or valid: state `pending_approval`, stop here. A PR that touches any file the policy cannot classify is **high**. Review rounds (3-round cap, findings answered) are a rule of the runner and of the task brief; Chaperone only counts them for `THRASH`.
6. **Title rule.** The squash commit header is the PR title: one Conventional Commit line, at most 72 characters (`AGENTS.md` / house rules). Refuse otherwise.
7. **Nothing moved.** Repeat steps 2 and 4 immediately before the write. Any change, refuse.
8. **Merge exactly H** (mint the write token now): `PUT /repos/{o}/{r}/pulls/{n}/merge` with body `{"sha": H, "merge_method": "squash", "commit_title": <title>}`. GitHub's documented meaning of `sha`: "SHA that pull request head must match to allow merge", and **409 if the head did not match** (<https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request>). That server-side compare is what closes the race between "I checked H" and "I merged"; it is the REST equivalent of `gh pr merge --match-head-commit`. 405/409/422 are returned to the caller as `OP_POLICY_REFUSED` with the GitHub status, with no retry.
9. **Confirm and clean up.** Re-read the PR: `merged == true`, record `merge_commit_sha`. Revoke the write token (`DELETE /installation/token`). Write `op.result` to the ledger with `external_ref` = PR URL (ADR-006).

`pr.update` (companion op, same policy shell): `PUT /pulls/{n}/update-branch` with `expected_head_sha` (422 if the head moved; <https://docs.github.com/en/rest/pulls/pulls#update-a-pull-request-branch>). This replaces `gh pr update-branch` in the procedure; a new head voids every earlier result, and the next `pr.merge` starts at step 2.

**Residual risk, stated plainly.** Between step 7 and step 8 another actor with write access can still advance the base. The per-repo mutex covers merges that go through Chaperone; it does not cover a human merging by hand in the GitHub UI. Closing that gap needs a merge queue or branch protection ("require branches to be up to date"), which is the deferred GitHub Team decision. The window is seconds, and the 409 on `sha` still guards the head.

## Alternatives

| Option | For | Against | Verdict |
| --- | --- | --- | --- |
| **GitHub App, token minted per run and per op by `chapd`** | Identity is a bot, not the operator; tokens expire in 1 h and can be narrowed to one repo and a permission set; revocable; no human-created long-lived secret; org-owned, survives a person leaving; free on any plan. | Cannot scope by branch (so we proxy pushes); App creation and key import are one-time human steps; stateless-token revocation needs the live revocation test (see Verify). | **Chosen** |
| Fine-grained PAT, one per project | Simple to start; no App registration. | Acts as the operator (audit trail lies); max one owner each; org policy can hold it `pending` and cap lifetime (366 days default); created by hand in the web UI `[INFERENCE: I found no REST endpoint to create one]`; cannot be minted per run or narrowed per operation; rotation is a human chore; expiry makes a quiet outage. | **Documented fallback only**: one token, one repo, `contents: write` + `pull_requests: write`, 30-day expiry, in the vault, behind the same push proxy and `pr.merge` algorithm. Switch only if the org blocks App creation |
| PAT (classic) | Works everywhere. | Broad `repo` scope, no per-repo limit; exactly the credential agents hold today. | Rejected |
| Deploy keys / SSH | Per-repo. | No PR/merge API; no checks API. | Rejected |
| Rely on GitHub rulesets or branch protection | Server-side, standard. | Not available on our private Free repos (cited above). | Deferred. When Team is bought, add rulesets as a second layer; the algorithm above stays |

## Verify

- Fake GitHub server tests for every refusal in steps 2-8; a **live** test against a scratch repo in `example-org` (not the example project) proving: narrowed token cannot touch another repo; token without `workflows` cannot push a workflow edit; `DELETE /installation/token` makes the token return 401.
- Push of `agent/<run>` accepted; push to base, a tag, a delete, a second ref in the same push, and a `push-cert` all refused.
- Replay of **18 Oct (merge on stale CI)** and **22 Oct (merge on red)**; head moves between steps 7 and 8 (fake server answers 409) refused with no retry; `verify` posted as a commit status by a PAT is ignored.
- Risk tiers: a low-tier PR merges with no approval; a medium or high PR returns `OP_APPROVAL_REQUIRED` until an approval bound to its head SHA exists; a file the policy cannot classify is treated as high; an approval for one head is refused for another head.
- Local CI (amendment 10): with a `pr.local_ci` policy, `pr.merge` accepts a check run of Chaperone's own App on exactly the head (`also` or `instead` of `verify`) and no other source (a same-named check from GitHub Actions or another App, a commit status); `ci.report` is orchestrator only, reads the repository, head and conclusion from chapd's own run record, and fails with a message naming the operator step while the App lacks `checks: write`.

## Amendments (2026-10-24)

**Amendment 1. Chaperone pushes.** The Decision section already had this shape; it is now a decision, not a proposal. The only GitHub write path an agent has is `chap` (`pr.open`, `branch.push` through the git proxy, `pr.update`, `pr.merge`). Tests verify it and replay "agent shell has no GitHub credential".

**Amendment 2. The agent account is a separate account.** "The agent's remote is `http://127.0.0.1:55398/git/...`" is unchanged. The agent account is a different Windows account from the operator's and from `svc-chaperone`, so `gh`/`git` credential helpers in the operator's profile are out of reach of agents. The reviewed setup script (run once by the operator, elevated) creates it.

**Amendment 3. Risk-tiered review.** Step 5 above. `pr.merge` for a low-tier PR is as before; medium and high add an approval. This replaces "workflow files need approval" as the only trigger; workflow files are one entry in the high tier. The tests gain the path classifier and the extra refusal and approval cases.

**Amendment 4. The orchestrator as a caller.** Step 1 "Authorize" accepts two kinds of caller: a run token (ADR-005) or the orchestrator token (ADR-007). For the orchestrator, `repo` must be in the token's project scope instead of equal to `task_scope.repo`, and the op must be in the token's op scope; all later steps are identical. The ledger events carry `requester.kind: orchestrator` and no `run_id`.

**Amendment 5. Step 3, latest `verify` run wins (operator, 24 Oct).** Read all `verify` runs of GitHub Actions on the exact head (`filter=all`), not exactly one. The most recent (highest `started_at`, then `id`) must be `completed/success`: an older failed run no longer blocks a green re-run, and an older green run never hides a newer red, queued, in-progress, cancelled or skipped one. A `verify` from another app or as a commit status, and a moved head, still refuse.

**Amendment 6. Push path as built (24 Oct).** `internal/gitproxy` serves `/git/<owner>/<repo>[.git]/{info/refs,git-upload-pack,git-receive-pack}`; the run token travels as the HTTP Basic password (libcurl, and so git, answers only a Basic challenge, so `chapd` sends `WWW-Authenticate: Basic` under `/git/`). A fetch is held to the run's repository (`SCOPE_PATH`) and is not an op. A push is recorded as a `branch.push` op: requested, allowed and executing in one transaction with `op.request`, then `op.result` (`succeeded`, `failed` from the report-status, or `unconfirmed` when GitHub's answer did not show whether the push landed). Refused with `SCOPE_BRANCH` before any byte reaches GitHub: a push certificate, more than one command, a delete, and any ref but `refs/heads/<task_scope.branch>` (the base branch and tags included). Git sends a bare flush-pkt ahead of a large push to test its credentials; it updates nothing, so the proxy forwards it as a discovery check and records no op. Each request mints a token for one repository (`contents: write`, `pull_requests: write`, `metadata: read` for a push; `contents: read` for a fetch), sends it as Basic `x-access-token`, never follows a redirect, and revokes the token when the request ends. `pr.open` is an adapter: a run may open a PR only from its own branch (`head == task_scope.branch`) into its base; the orchestrator may name any head in a project that has a `pr:` policy block.

**Amendment 7. `pr.open` needs `contents: read` (25 Oct 2026).** The first runs started by the runner got `422 Validation Failed` from `POST /pulls`: the token held `pull_requests: write` and `metadata: read` only, and GitHub cannot check the head branch without reading refs (`errors[]`: resource `PullRequest`, code `custom`, message `not all refs are readable`; the same call with `contents: read` added answered 201). Checked live against `chaperone-sandbox` with the App key: `pr.open` now asks for `gh.PermsOpenPull()`; `deploy` records a deployment with `deployments: write` alone (201, also tried live); `pr.merge` and `pr.update` hold `contents: write` for their one write, which includes the ref reads of `update-branch`, and read with `contents: read`. One test per op pins each set (`internal/ops/op_permissions_test.go`, `deploy_perms_test.go`, `internal/gitproxy` `TestProxyTokenPermissionsPerGitCall`). The client now keeps a 422's `errors[]` (`gh.APIError.Errors`, `Detail()`), so the denial text and chapd's log show GitHub's reason.

**Amendment 8. The git proxy repeats a 404 with the same token (26 Oct 2026).** From about 12:20 on 26 Oct, about 60% of VM clones through the proxy failed with `404 repository not found`, in runs of failures, for a repository the App can see. GitHub support's own explanation of this symptom: a new installation token "needs to be replicated to all of our edge cache sites to be usable on them", with edge traffic growing; until it is, a private repository answers 404. They advise a first retry after a few seconds and more later (<https://github.com/aws-amplify/amplify-hosting/issues/4080>; same pattern, always on a token's first requests, in <https://github.com/akuity/kargo/issues/5610>). Our own live test saw the mirror image: a revoked token kept working for about 3 s (`internal/gh/live_test.go`). The per-request token (amendment 6) is unchanged. Item 1’s table would allow one token per run and repository, but that does not help: the first use of every token is the one that 404s, and it would add a cache that must be revoked when the run ends (ADR-005). Instead `forward` repeats a request that GitHub answered 404, with the same token, after 0.5 s, 1 s and 2 s (`Handler.RetryDelays`), only while the request can be sent again byte for byte: no body, or a body of known length up to 1 MiB, which `forward` holds in memory. A 404 comes before GitHub applies anything, so a repeated push cannot apply twice. A chunked or larger body is sent once and a 404 is final. Each repeat writes one `Info` line without the token; after the last repeat a 404 is still reported as a not-found error. Nothing else (401, 403, 5xx) is repeated.

**Amendment 9. The git proxy keeps one token per run, repository and permission set (operator decision, 26 Oct 2026).** This replaces two sentences: amendment 6's "revokes the token when the request ends" and amendment 8's "The per-request token (amendment 6) is unchanged". amendment 8 rejected a per-run token because it "would add a cache that must be revoked when the run ends". The operator approved that cache, for this reason: minting and revoking a token for every HTTP request cost about four GitHub API calls per clone, and every request used a token for the first time, which is the use that GitHub answers 404 (amendment 8). With the cache, a clone, a fetch and a push use two tokens in all (one per permission set), and only the first request of each is a first use. This is what item 1's table already allowed ("memory, until the run ends"). As built in `internal/gitproxy/tokens.go`:

- **Key and permissions.** The cache key is the run ID, the repository and the permission set. A fetch (`gh.PermsFetch()`, `contents: read`) and a push (`gh.PermsPush()`) are different keys, so a fetch never holds a write permission and a push token is only minted by a push request (`TestProxyTokenPermissionsPerGitCall`). `pr.open`, `pr.merge`, `pr.update` and `deploy` do not use the cache: each still mints its own token for one operation and revokes it (item 1).
- **First use is single-flight.** Two simultaneous first requests with the same key mint once; the second waits for the first mint. A failed mint is not remembered.
- **Expiry.** A cached token is reused while it has more than 5 minutes before `expires_at` (`Handler.TokenMargin`); after that the next request mints a new one. The old token has not expired and a running request may still hold it, so it is kept and revoked with the others at run end. A token for which GitHub answers 401 (revoked by someone else, say) is revoked and dropped at once; a 403 or a 404 is not about the token and drops nothing.
- **Run end.** `runtoken.RunsConfig.AfterEnd` calls `Handler.EndRun(run_id)`, after the end committed (ADR-005 "End"). It runs for every way a run ends (the runner's end call, an operator revoke, the reaper). It takes the run's tokens out of the cache and remembers the run as ended for an hour, so a request that was admitted before the end cannot mint a new token, or leave one behind, for a run that is over; then it returns. A request of an ended run is refused by the token verifier as before (`TOKEN_REVOKED`); the cache refuses it the same way if it gets that far. The tokens are revoked on GitHub (`DELETE /installation/token`, all at once) in the background, on a context that outlives the caller and ends after 15 seconds, so a GitHub outage does not slow the end of a run or `runner stop --all` (`TestEndRunReturnsWhileGitHubIsStuck`).
- **Shutdown.** `App.Close` calls `Handler.Close`, which revokes every token of every run and waits for the revokes `EndRun` left running, best effort: a token that cannot be revoked expires within the hour. After it the proxy mints nothing.
- **Where tokens live.** In chapd's memory, in `gh.Token` values that never print. They are not logged and not sent to the VM, and a crash loses them (they then expire on their own within the hour, as a revoke that failed does). The log line for a mint names the run and repository, never the token.
- **amendment 8 stays.** A 404 on a token's first use is still repeated with the same token after 0.5 s, 1 s and 2 s. It now matters only for the first request of each key.
- **A caller that is not a run** has no run to end a token with, so it gets a single-use token, revoked after the request. The gate refuses such callers; this is a fallback only.

Residual risk, stated plainly: a token lives up to an hour (less the margin) instead of one request, so a bug that leaked one from chapd's memory would be usable for longer. The scope has not changed: one repository, the permissions above, and the run's end or chapd's stop revokes it.

## Amendment 10 (31 Oct 2026): `pr.merge` may accept a local CI result, posted by Chaperone's own App

**Why.** The factory repos (`chaperone`, `runner`, `factory-spec`) run their Linux checks on a PR head in a runner room (`runner ci <project> <sha>`), not on GitHub-hosted runners. That result has to reach `pr.merge`, and step 3 reads only GitHub Actions' `verify` (app 15368), so that no one else can post a fake one. This amendment lets a project say, in its policy file, that a second source counts, and keeps every other source out.

**What step 3 accepts, when the project's `pr:` block has `local_ci`.** `local_ci` has two members: `mode` and `check` (the check run's name, 1 to 64 characters, default `local-ci`; `verify` and the names in `extra_checks` are refused, so one name never has two sources).

- `mode: also`: step 3 needs `verify` and the `extra_checks` from GitHub Actions, **and** the local check.
- `mode: instead`: step 3 needs the `extra_checks` from GitHub Actions and the local check; it does not read `verify`. Use it when the hosted Linux job no longer runs on PRs.
- No `local_ci` block: step 3 is as before, byte for byte. The default is off.

The local check is found like the others (`GET /commits/{H}/check-runs?check_name=<check>&app_id=<own>&filter=all`, latest run by `started_at` then `id`, `completed/success`, `head_sha == H`, amendment 5), with one difference: **`app_id` is the numeric ID of Chaperone's own App**, read from `GET /repos/{o}/{r}/installation` (the configured App ID may be the client ID, which a check run's `app.id` is not). The code repeats the filter on each returned run. So a check of that name from GitHub Actions, from another App or from a commit status (which has no App behind it, so a person's token can post one) never counts. Only the App can create a check run, and GitHub records which App did. A report is for exactly one head: a push gives a new H and the old report does not apply (`CI_STALE`); a red report is `CI_RED`. Steps 2 and 4 to 9 are unchanged. In particular **step 5 is unchanged: a PR that touches `.github/workflows/**` is still high tier and still needs a card**, so a PR cannot edit its own checks without a human reading the diff. `deploy` still reads `verify` from GitHub Actions on the base branch: hosted Linux CI keeps running on `main`.

**The op that posts it: `ci.report`.**

**Operator step (once, before the op can work).** The App holds `checks: read` today. In GitHub, Settings, Developer settings, GitHub Apps, `chaperone-app`, Permissions, set **Repository permissions, Checks, to Read and write**, and save. GitHub then asks the organisation owner to approve the changed permissions on the installation (`example-org`, which holds `chaperone`, `runner` and `factory-spec`); until the owner accepts, a token request for `checks: write` answers 422 and `ci.report` fails with a message that names this step and posts nothing. No key changes and nothing is re-imported. Steps: `docs/runbooks/ci-report.md`. [INFERENCE: that an installation can accept a permission upgrade without being re-installed is GitHub's documented behaviour, not tried here.]

**What is trusted, stated plainly.** `pr.merge` on a `local_ci` project trusts: chapd's own record of the run, whose repository and commit the runner signed into the run token (ADR-005) and whose outcome is what the runner's end call said; and the runner's `ci` profile, which must take its verdict from the exit code of the checks as measured by its supervisor and its plan from the base branch's workflow, not from files the code under test can write (see the runner's own design record). Chaperone does not look inside the room. What Chaperone adds is that the reported commit, repository and conclusion cannot come from the caller, that only the orchestrator can ask, and that the result is a check run whose App GitHub itself records. The hosted Linux job on `main` and the weekly scan stay as the backstop that compares a room's report with GitHub's own run.

**Tests.** The `pr.merge` tests gain: with `also`, a green local check alone and a green `verify` alone both refuse; with `instead`, a green local check merges with no `verify` and a red one refuses; a `local-ci` check from GitHub Actions, from another App, in progress or neutral never counts; a report for an older head is `CI_STALE`; the latest report wins; without a `local_ci` block the App's check is ignored. `ci.report` gains one test per refusal above, the posted check run per outcome, the token's permissions, the missing-permission message, and a round trip through `pr.merge`. The existing test that a `verify` posted as a commit status by a PAT is ignored stays.

**Not changed.** Steps 1, 2, 4 to 9, the per-repo mutex, the 409 on `sha`, amendment 5, and the rule that no agent holds a GitHub credential. The residual risk of ADR-002 stands: another actor with write access can still move the base between steps 7 and 8.

**Amendment 11. Issue ops for a monitoring job (31 Oct 2026).** A monitoring job on the host files GitHub issues **through Chaperone**, with no GitHub credential of its own (amendment 1 holds). Three ops, `issue.open`, `issue.comment` and `issue.reopen`, class routine (`internal/ops/issue.go`). The App needs one permission it was not given for ADR-002 item 1: **Issues: read and write**. A token for these ops asks for `issues: write` and `metadata: read` only (`gh.PermsIssueWrite()`; `issue.comment` and `issue.reopen` first read the target with `gh.PermsIssueRead()`): no `contents`, no `pull_requests`. Each token is minted for the one call and revoked, like `pr.open`'s.
- **Who.** Only an orchestrator token. No run profile lists the ops (a run is refused `OP_NOT_IN_TOKEN`) and the adapter also refuses a run caller. The monitoring job gets its own orchestrator token (ADR-007) scoped to these three ops and one project: [`runbooks/issue-ops.md`](../runbooks/issue-ops.md).
- **Where.** The repository is the project's `pr.repo` (for the example project, `example-org/storefront`), never the caller's: another repository is `SCOPE_PATH`.
- **The label rule.** The label is `source:error-watcher` (`ops.IssueLabel`, exact match). `issue.open` is refused unless `params.labels` includes it. `issue.comment` and `issue.reopen` read the issue first and are refused when it lacks the label, when it does not exist, or when GitHub's issues API is answering for a pull request. `Execute` reads the issue again with the token that writes, so a label removed after `Check` stops the write.
- **Limits.** Title 200 characters on one line, body 10 000 bytes, at most 10 labels of 50 characters; unknown params are refused. Rate: the baseline gives each op `rate_per_minute: 6` and the new `rate_per_hour: 20`, per caller and op (a policy pack field; a project file may add or lower an hourly cap, never lift one). Over either is `OP_POLICY_REFUSED` with `Retry-After`.
- **Tier.** Routine: allowed with no human step, because the label rule, the repository, the caps and the token's scope bound what the monitoring job can do. A secret in a title or body is refused whole by the redaction check before anything is stored.
- **Not decided here.** Creating the label on the repository (GitHub creates a label named in `labels` when the token may write issues; the operator may create it first with a colour and description). Closing issues: the monitoring job cannot close one; a person or the triage flow does.

**Amendment 12. Read ops for a pull request: `pr.view`, `pr.diff`, `pr.checks`, `pr.files` (1 Nov 2026).** The dashboard (an optional, separate web front end) needs to read a pull request without holding a GitHub credential: it reads GitHub only through Chaperone (amendment 1 holds). Four ops, class routine, reversible, read-only (`internal/ops/pr_read.go`). **They shipped off in the baseline and are on since the operator's policy PR** (`enabled: true` in `internal/policy/data/baseline.yaml`, and the four names in `shippedEnabled` in the policy test); they take effect when `chapd` is reinstalled from that commit. Nothing else changes for an existing install.
- **Who.** Only an orchestrator token whose scope lists the op (`chapd orch issue -ops pr.view,pr.diff,...`). No run profile lists them and the adapter refuses a run caller. A client of the dashboard's own, with a token kind of its own, is a later change; it will be a third caller kind for the same adapters.
- **Where.** The repository is the project's `pr.repo`, never the caller's: another repository is `SCOPE_PATH`, and a project with no `pr:` block is refused. The target is `{adapter: github, ref: "owner/repo#N"}`.
- **What each returns.** `pr.view`: number, title, body (cut at 64 KiB, `body_truncated`), state, draft, merged, author, labels, head {ref, sha, repo, fork}, base {ref, sha}, `mergeable` (null while GitHub computes it, with `mergeable_state` `unknown`), URL, times and counts. `pr.diff`: the unified diff, cut at a line end at 256 KiB (`truncated`, `size`, `returned`, `cap`), and the head sha it was read at. `pr.checks`: the latest check run of each name on the head commit (id, name, status, conclusion, app id, URL, start time) and counts (`passed`, `failed`, `pending`, `other`); commit statuses are not check runs and are not listed, and a head with more than 100 check runs fails rather than answer partly. `pr.files`: one page of the changed files (`page`, `per_page` up to 100, default 30; GitHub lists at most 3000), with name, previous name, status, additions, deletions and whether GitHub sent a patch; no patch text (that is `pr.diff`), `total` and `has_more`. `pr.diff`, `pr.checks` and `pr.files` take an optional `expected_head_sha`: if the head is another commit the op fails and says the new head, so a caller cannot show a diff for one head beside a card for another. (The head is read once, before the second GitHub call; a push between the two calls is not caught, which is why `pr.merge` still checks the head itself.)
- **Token.** One installation token per op, minted after the last check, narrowed to the repository, **read only**: `pull_requests: read` and `metadata: read`, plus `checks: read` for `pr.checks` (`gh.PermsReadPull`, `gh.PermsReadPullChecks`). No `contents`, no write. It is revoked when the op ends. The App already holds these permissions (ADR-002 item 1 and amendment 10): no operator step in GitHub.
- **Secrets and untrusted text.** A title, body, diff or check name is a person's text. It is data for the reader, never an instruction, and `chap` says so above it and replaces control characters. Every result passes chapd's redaction before it is stored (ADR-003): a result that holds anything shaped like a registered secret (a token in a PR body, a key in a diff) is stored as `{"blocked":"REDACTION_BLOCKED"}`, whole, and the caller gets that. Nothing of a result goes into the ledger: the events carry the op, the target, the outcome and the hashes, as for every op.
- **Limits.** Per caller and op, per minute and per hour: `pr.view`, `pr.checks`, `pr.files` 30 and 600; `pr.diff` 12 and 240 (it costs two GitHub calls and the most bytes). Over either is `OP_POLICY_REFUSED` with `Retry-After`. A project file may lower a cap, never lift one. chapd never retries a GitHub call; GitHub's own rate-limit refusal comes back as a failed op with its retry time (`retry_after_seconds`), and the caller decides.
- **Failure is `failed`, not `unconfirmed`.** A read writes nothing, so a GitHub 5xx, a missing pull request or a missing App permission is a failed op with the reason in `result.error`, and the caller may ask again. A dry run, an approval request and a release re-check never reach GitHub: `Check` validates the request and nothing more.
- **Ledger.** Like every op: one `op.request` and one `op.result` (outcome `succeeded` or `failed`) from the orchestrator, in the same transaction as the state change, and a `denial` for a refusal.
- **Tests.** `internal/ops/pr_read_test.go` and `pr_read_service_test.go` against the fake GitHub (`ghtest`): each op's result; the token's permissions (read only, no `contents`); every refusal (run caller, other repository, other owner, project without `pr:`, bad target, unknown or malformed param, bad head); the diff cap at a line end and on a character boundary; a moved head; paging, including past GitHub's 3000-file cap; failures (404, 5xx, 406, primary and secondary rate limit, missing permission, more than 100 check runs); that the baseline has them on as routine reads and no profile lists them; the rate limits; that a secret in a body or diff is never stored or returned; the ledger. `internal/gh/pullread_test.go` covers the client calls and `cmd/chap` the commands (golden files).

**Amendment 13. Names of the read ops against the connector standard (5 Nov 2026).** The connector standard (a design document outside this repository) says op names are frozen once they are in signed tokens, and the operator's policy change turned the four read ops of amendment 12 on, so the orchestrator's token holds them. The standard's own GitHub names for the same capabilities are `pr.get` and `pr.list`. Decision: **no rename and no second op.** `pr.view`, `pr.diff`, `pr.checks` and `pr.files` keep their names. The mapping lives in data, `connectors/github.yaml`: `pr.view` has `standard_name: pr.get` (it is the standard's `pr.get`, under its legacy name); `pr.checks` is already the standard's name; `pr.diff` and `pr.files` are additions the standard does not have (`extension: true`). The standard's `pr.list` is not built (`standard_not_built`). When the standard's GitHub slice is built for keys, a key preset names the ops by their built names, and a second forge adapter (GitLab, Azure DevOps) implements `pr.get` under that name; the profile test (C19, `internal/policy/profile_test.go`) refuses a mapping that shadows an op of the catalog, so `pr.get` can never become a second name for `pr.view` by accident. The alternative (rename while the ops are off) was not available: they are on. Nothing in `api/manual.yaml`, the baseline pack, an orchestrator scope or a run profile changed for these four ops.
