# ADR-009: A local MCP front end (`chap mcp`)

- **Status:** **Accepted** for step 1 (operator, 3 Nov 2026: "a LOCAL MCP front end (stdio; Claude Code / Codex / Cursor on the same machine; no internet exposure, no ID-JAG)"). Step 2 (an internet endpoint, then Enterprise-Managed Authorization) is **gated on the day-90 demand test** and is not decided here. Written 2026-11-05.
- **Decides:** how an MCP client on the same machine uses Chaperone's op catalog without a second way in: the shape, the protocol support, the credential, the tool mapping, and the rule that the front end never shows or changes an approval card.
- **Inputs:** ADR-001 (language, dependency policy), ADR-004 (approvals: only the console decides), ADR-005 and ADR-007 (run and orchestrator tokens), `api/openapi.yaml` (`/v0/catalog`, `/v0/ops`, `/v0/approvals`), the MCP specification revision 2026-07-28 (versioning, stdio, tools, discovery), and the custom-keys specification draft, section 7.11.

## Context

- Claude Code, Codex and Cursor speak MCP. Today none of them can reach Chaperone, so a developer who wants "my agent reads this PR" has to hand it a vendor token, which is the thing Chaperone exists to prevent.
- `chap` is already the one client of `chapd`: it loads the credential, refuses a non-loopback address, never follows a redirect and masks every secret it prints. An MCP front end that talked to `chapd` another way would be a second client to audit.
- The approval card is signed text rendered by `chapd` and shown by the console (ADR-004). Whatever shows an agent's request to a human must not be something the agent's own tool can write.
- MCP has two eras. The handshake era (`initialize`, a session) and the revision 2026-07-28, which has no handshake: every request carries its protocol version in `params._meta`, and `server/discover` tells a client what the server supports. A dual-era server picks the behaviour from how the client opens.

## Decision

**`chap mcp` is a subcommand of `chap` that speaks MCP over stdio to the client that started it. It is a translator: one tool call is one request to `chapd`, with the caller's own credential, through the code `chap` uses. It decides nothing.**

1. **Shape.** `chap mcp` takes no arguments. It reads JSON-RPC from stdin and writes it to stdout, one message per line; diagnostics go to stderr and never hold a request, an argument or a result. It opens no listener. The package behind it, `internal/mcpfront`, imports neither `net` nor `net/http`, and a test checks the import list.
2. **Same door as `chap`.** The package talks to `chapd` through a `Backend` interface; `cmd/chap` implements it with the same `call` as every other command: `CHAP_RUN_TOKEN`, else the orchestrator token file; `CHAP_URL` only if it is a loopback address; no redirect. Policy, approvals and the ledger therefore apply exactly as for the command line, and there is no new bypass: there is no path in the package to any route but `GET /v0/catalog`, `POST /v0/ops`, `POST /v0/approvals` and `GET /v0/ops/{id}`. `CHAP_PROJECT` names the project (an orchestrator must).
3. **Credential from the environment and files, as the MCP authorization page advises for stdio.** No OAuth, no ID-JAG, no token in an argument. The process outlives a reissued orchestrator token, so when the credential came from the orchestrator token file, a `401` makes it read the file again once. A `401` is not free: `chapd`'s auth path records a ledger denial for it and it counts toward the thrash flag, so the retry is made only for the file (which can change) and never for `CHAP_RUN_TOKEN` (which cannot change while the process runs); a revoked file token writes two denials for the call. A client with no credential still starts: the one tool `chaperone_setup` says what is missing.
4. **Tools are the caller's catalog.** `tools/list` calls `GET /v0/catalog`, which `chapd` narrows to the ops this credential may use. Each enabled op on the `op` surface is one tool; the git surface is not an op call and has no tool. The description is the catalog's `summary` plus the op's class, reversibility, whether it needs approval, and the contract's text about its target. The input schema is generated at run time from the contract: the `Params<Op>` component of `api/openapi.yaml` (`pr.view` is `ParamsPrView`), inside an envelope of `target`, `params`, `project`, `reason`, `dry_run`, `wait`, `approval_id`, `request_approval`. The file is embedded in the binary, so the schema cannot drift from the contract; a test fails when an op has neither a Params component nor a line in a list kept for the purpose, or a Params component has no op. **The schema is guidance, not a check here:** `chap mcp` refuses unknown argument names and wrong JSON types before anything is sent (and a bad `op_id`, the one value that goes into a URL path), but it does not check `params` against the schema's patterns, lengths or enums. `chapd` validates every call and refuses one that does not fit, so `chapd` is the validator; each tool description says so.
5. **Tool names.** Clients accept only letters, digits, `_` and `-` in a tool name, so the dots of an op name become underscores: `pr.view` is `pr_view`. The mapping is one to one for every op name the catalog allows. (The spec's "named exactly as the op" cannot hold for the dot; the description and every result name the op itself.)
6. **Fixed tools:** `chaperone_manual` (the caller's ops), `chaperone_op_status` (follow an op by id, waiting up to 55 seconds) and, only when the catalog cannot be read, `chaperone_setup`. The key tools of the spec (`chaperone_key_*`) belong to the custom-keys work (the reserved ADR-008) and are not part of this step.
7. **Results.** *Allowed:* structured data, with whatever the op read from outside kept in a field named `untrusted_result` behind a fixed notice line, which is in the text and also a fixed `untrusted_notice` field of `structuredContent`, so a client that shows the model only the structured part still carries the warning. *Refused:* an error result with the cause, the reason and a next step; the first lines are `chap`'s own denial text (the same renderer), with its `request: chap request ...` line dropped. The result has exactly one `next:` line, and `structuredContent.next` is the same text. If the rendered denial already has one (a stale branch, an approval flood, an expired token), that is the line and nothing is added; only a denial with none gets the MCP line (`request_approval=true` with a reason, or "asking is not possible"). The same holds for an op that ended denied. *Pending:* not an error; see 8. *Failed or expired:* an error result with the cause. A secret-shaped value is masked by the same scrubber as `chap`, value by value and again over the whole line.
8. **The no-card rule.** A call that needs a human returns exactly: status, state, op id, approval id, class, seconds left, and one fixed sentence that tells the model to call `chaperone_op_status`. Nothing from the op, its reason or its approval is copied, and each id is checked against its shape before it is copied. The package imports nothing from `internal/approvals` or `internal/console` and has no route that decides, edits or reads a card. The human sees the card only in the console (or framed in the optional dashboard), which is the property step 2 must keep.
9. **Both eras.** A request with the version in `_meta` is served as modern (results carry `resultType: "complete"`; an unsupported version gets error `-32022` with the supported list); `server/discover` is answered; `initialize` is answered with the client's version if it is a handshake revision this server knows (2025-11-25, 2025-06-18, 2025-03-26, 2024-11-05), else the newest of them. A request with neither is served as legacy. Calls run concurrently, at most 8 at a time: a ninth gets error `-32001` at once, nothing queues, and a request id that is still in flight gets `-32600` instead of replacing the first. `notifications/cancelled` stops one and sends nothing more for it. The server exits when stdin closes after answering what is in flight, and also when it gets SIGINT or SIGTERM, even while stdin stays open (calls in flight are cancelled and get no reply). Batches (removed from the protocol in 2025-06-18) are refused with `-32600`; so is valid JSON that is not an object and a message with an `id` but no `method`, `result` or `error`. A message over 8 MiB gets `-32600`, is skipped to the next newline, and the server keeps serving.
10. **Not in step 1:** any HTTP transport, OAuth, ID-JAG, a hosted endpoint, MCP resources, prompts, elicitation, subscriptions, a list-changed notification (a client reads `tools/list` again, and the list follows the credential), and the key tools.

## Dependency: hand-written, not the SDK (ADR-001 amendment 7)

Facts checked on 2026-11-05: the official Go SDK (`github.com/modelcontextprotocol/go-sdk`) is active (v1.8.0, 2026-09-14) and supports revision 2026-07-28. Its licence is mixed: new work is Apache-2.0, contributions not yet relicensed stay MIT (the repository's `LICENSE` says so, and GitHub reports "NOASSERTION"). Its `go.mod` requires Go 1.25 and, besides modules Chaperone already vendors (`golang-jwt/jwt/v5`), `google/jsonschema-go`, `segmentio/encoding` (and `segmentio/asm`), `yosida95/uritemplate/v3`, `golang.org/x/oauth2`, `golang.org/x/time` and `golang.org/x/tools`. It would be vendorable; **I did not vendor it or build against it.**

This ADR picks the hand-written server: it was the recommendation on the operator's open question; the surface used (JSON-RPC over stdio, `initialize`, `server/discover`, `ping`, `tools/list`, `tools/call`, `notifications/cancelled`) came to about 1,500 lines with comments, schemas and result mapping included, both eras served; Chaperone's allowlist exists so that the supply chain of a security product stays small, and an OAuth client and an HTTP server are dependencies a stdio-only front end does not use; and the no-listener property is easiest to prove when the package cannot import one. The cost is that a protocol change is ours to follow. **Flip condition:** step 2 (an HTTP endpoint) needs an SDK-sized amount of protocol, and OAuth, so the choice is revisited there, with the licence question settled.

No module is added. `go.yaml.in/yaml/v3` (ADR-001 amendment 6) gains a second importer, `internal/mcpfront`, which reads the contract's Params schemas.

## What this does and does not defend

| Attacker or mistake | Result |
| --- | --- |
| A prompt injection in a PR body, issue or diff that the agent reads | It arrives in `untrusted_result` behind a notice and changes nothing in the server: a result never causes a call (a test feeds an injected instruction and asserts one request reached `chapd`). The model may still be fooled; the next call is still checked by `chapd`'s policy and, if risky, by a human at the console. |
| An agent that wants to approve its own request | No tool, no route. `chapd` has no approve route for any token; the front end only reports "pending" and never shows the card. |
| An agent that wants the human to approve something other than what it asked | The card is rendered by `chapd` from the stored request; the agent writes only the reason, shown as untrusted. The front end adds nothing to either. |
| A process that points the client at another address | `CHAP_URL` must be loopback; a redirect is not followed. |
| A secret in a result | Masked by `chap`'s scrubber; `chapd` already refuses a secret-shaped body (`REDACTION_BLOCKED`). |
| A stale orchestrator token in a long-lived process | One re-read on `401`, only when the credential came from the orchestrator token file; then the refusal is reported. A `CHAP_RUN_TOKEN` is never retried. |
| Anything running as the user that can start `chap mcp` | It has the user's own credential, as it has for `chap`. That is the same exposure as ADR-007 states; MCP adds no authority. |

## Verified, and not

- **Claude Code 2.1.302** (installed on the server): its health check connected to `chap mcp` (`claude mcp list`: Connected) in a scratch configuration against a fake `chapd`. A capture of its first messages shows it negotiates the **modern revision**: it sends `server/discover` with the id `"server-discover-probe-1"` and `_meta` protocol version `2026-07-28`, then `tools/list` with the same `_meta`. No model call was made, so a real tool call by Claude Code is **not verified**.
- **Codex 0.149.1** (installed): `codex mcp add` wrote the expected `config.toml` entry and `codex mcp list` showed it enabled; `codex mcp list` does not start the server, so a Codex handshake was **not verified**, and the revision it negotiates is not known.
- **Cursor:** not installed; **not verified**.
- Both eras are tested over pipes against a fake `chapd` (`cmd/chap` `TestMcpTranscriptBothEras`), with the handshake-era transcript written from the specification, not captured from a client.

## Alternatives

| Option | For | Against | Verdict |
| --- | --- | --- | --- |
| Hand-written stdio server in `chap` (this ADR) | One client of `chapd`; no listener; no new module; both eras | Protocol changes are ours | **Chosen** |
| The official Go SDK | Maintained; does 2026-07-28 | About eight modules the allowlist does not have, a mixed licence, OAuth and HTTP code a stdio server never runs | Revisit at step 2 |
| A separate `chap-mcp` binary | Own release cycle | A second client of `chapd` with its own credential loading and scrubber | Rejected |
| An HTTP MCP endpoint in `chapd` | One process | An internet-reachable surface beside the approval console, before the demand test | Rejected for step 1 (gated, step 2) |
| Tools named exactly as ops, with dots | Matches the contract | Clients rewrite or reject a dot, so the name the model sees differs by client | Rejected: underscore, one to one |
